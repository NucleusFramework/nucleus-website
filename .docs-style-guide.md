# Nucleus docs — writing style guide (v2)

This is the **binding** style for every page under `content/docs/`. It replaces the
marketing-tinted voice described in `.writing-brief.md`. When the two conflict, this file wins.

The target register is the JetBrains **Kotlin Multiplatform docs**, specifically
`topics/quickstart.md` (cloned locally at `/tmp/kmp-dev-docs/topics/`). Read that file
before writing. The goal is that a reader can't tell our docs and the KMP docs apart.

---

## 0. Plug and play (binding since 3.0)

Write like the Electron docs: the reader wants to use the feature, not learn how Nucleus builds it.

- A page shows **what the feature does, a working snippet, the options, and the platform
  differences that change the code you write**. Nothing else in the main flow.
- **Cut** internals that never change what the reader writes: native API names (AppKit, GDK,
  Win32 calls, Wayland protocols), internal Kotlin types, timings and factors, PR numbers,
  how the plugin patches or generates things, measurements.
- **Hide** internals that help when something goes wrong in one collapsed block at the end of the
  page, before the API reference:
  ```mdx
  import { Accordion, Accordions } from 'fumadocs-ui/components/accordion';

  <Accordions>
  <Accordion title="Under the hood">   {/* FR: "En coulisses" */}
  - short bullets
  </Accordion>
  </Accordions>
  ```
  At most one such block per page. Omit it when nothing qualifies.
- No `## How it works` section in the main flow. Its useful part goes in the accordion.
- No "Add the dependency" section when the module comes with `nucleus-application`: say so in
  the lede in half a sentence.
- Keep flags, system properties and gotchas the reader acts on, in one line each.
- Gold standard: `content/docs/input/trackpad-gestures.mdx`.

## 1. Voice

- **Second person, present tense.** Address the reader as "you". Use the imperative for
  instructions: "Add the dependency", "Run the app", not "We will add" or "The user should add".
- **French pages use vouvoiement** ("vous"), never "tu".
- **Neutral and factual.** State requirements and behavior plainly. No hedging
  ("you'll probably want", "it may be possible"). KMP writes: *"The plugins necessary for
  Kotlin Multiplatform require at least IntelliJ IDEA 2025.2.2."* — copy that flatness.
- **No marketing.** Delete hype adjectives and sales framing. Banned words/phrases:
  *blazing, first-class, unlocks, productized, rounds out, real desktop framework,
  peak throughput, instant, store-ready, à la carte, powerful, seamless, effortless,
  cutting-edge, best-in-class*. Say what the thing does, not why it's great.
- **No "why care?" ledes.** Do not open a page selling the reader on the feature.
  Open by stating what the page covers or what the API does.
- **Explain, don't sell.** A comparison table is fine when it's factual; superlatives are not.
- **Run every page through the stop-slop rules** (`.claude/skills/stop-slop/`): no em dashes in
  prose, no filler adverbs, no "not X, it's Y" reframes, active voice, varied sentence length.
- **Tao is not a choice.** Since 3.0 Tao is the only window backend. Do not frame it as a backend
  to pick; name it only where the reader types a Tao identifier (`TaoWindow`, `-Dnucleus.tao.*`).

## 2. Page opening

- **No H1** — the frontmatter `title` renders the heading. The first line of the body is the lede.
- **Lede = 1–2 plain sentences.** State what the page covers or what the module does.
  - Tutorial/procedural page: `In this tutorial, you'll ...` / `On this page, you'll ...`
  - Reference/module page: `<Module> lets you <do X> from Kotlin.` Then one sentence on scope.
- **Kill `## TL;DR` entirely.** The KMP docs have no TL;DR blocks. Remove them everywhere.

## 3. Headings

- **Task-based imperative** for anything procedural: `Set up the project`, `Add the dependency`,
  `Send a notification`, `Run the app`, `Package the app`, `Sign the build`.
- Reference sections may use noun headings (`API reference`), but the sub-headings under them
  should still be task-oriented (`Build a notification`, `Send`, `Check availability`).
- Sentence case, not Title Case: `Run the app`, not `Run The App`.
- Keep the closing section titled exactly **`## What's next`** (FR: `## Et ensuite`).

## 4. Structure per archetype

Full conversion applies to every page. Use the skeleton that matches the page's job.

**A. Getting-started / tutorial** (`start/*`, `migrate/*`, packaging how-tos, CI/CD):
```
<lede: "In this tutorial, you'll ...">
## Before you start          (prerequisites, as a bullet list — optional)
## <Step 1 imperative>       (numbered steps inside, code per step)
## <Step 2 imperative>
...
## What's next
```

**B. Reference / module page** (`os/*`, `lifecycle/*`, `performance/*`, `ecosystem/*`):
```
<lede: "<Module> lets you ... from Kotlin.">
## Add the dependency        (only for optional modules; verified coordinate)
## <Primary task>            (minimal working snippet first, then prose)
<Accordion "Under the hood"> (optional, collapsed; see §0)
## API reference             (organized by task, not by class)
## Notes                     (only if real gotchas — else omit)
## What's next
```

**C. Concept page** (`concepts/*`, section `index.mdx`):
```
<lede: plain statement of the concept>
## <named subsections>       (noun or task headings, whichever reads plainer)
## What's next
```

- The site `index.mdx` and `why-nucleus.mdx` are the only overview pages; keep them
  informative but still strip hype. They may keep a short feature list (no `## TL;DR` label).

## 5. Admonitions (Writerside → Fumadocs)

The KMP docs use `> ... {style="note"}`. We render with Fumadocs `<Callout>`:

| KMP / intent            | Fumadocs                          |
|-------------------------|-----------------------------------|
| `{style="note"}`, info  | `<Callout type="info">`           |
| tip                     | `<Callout type="tip">`            |
| warning / caution       | `<Callout type="warn">`           |
| error / danger          | `<Callout type="error">`          |

- Keep callouts **short and single-idea**, like KMP. One or two sentences.
- Add the import once, right after frontmatter:
  `import { Callout } from 'fumadocs-ui/components/callout';`

## 6. Tabs (platform / tool variants)

KMP uses `<tabs><tab>` heavily for platform-specific paths. We use:
```mdx
import { Tab, Tabs } from 'fumadocs-ui/components/tabs';

<Tabs items={['macOS', 'Windows', 'Linux']}>
<Tab value="macOS"> ... </Tab>
<Tab value="Windows"> ... </Tab>
<Tab value="Linux"> ... </Tab>
</Tabs>
```
Use tabs for genuinely divergent per-OS or per-tool instructions, not to hide length.

## 7. Code

- Kotlin 2.x, Compose Multiplatform, JDK 17+. Gradle: `build.gradle.kts` (Kotlin DSL).
- **Show imports** when the type isn't obvious. Runtime types live under `dev.nucleusframework.<module>.*`.
- Add a filename title to build snippets: ```` ```kotlin title="build.gradle.kts" ````.
- Shell blocks use `shell` (matches KMP), e.g. ```` ```shell\n./gradlew run\n``` ````.
- **Verified coordinates only.** The Maven group is `dev.nucleusframework`; artifacts are
  `nucleus.<module-name>`. Prefer the `<version>` placeholder (injected at build from
  `lib/versions.json`). If you hardcode a number, use the live line from
  `lib/nucleus-version.ts` (`NUCLEUS_VERSION`, currently 3.0.0) — never leave an older minor.
  Never document an artifact that is not in the source's `settings.gradle.kts`.
- Placeholders: `com.example.MyApp`, `myapp`.

## 8. Fact-checking protocol (non-negotiable)

Before writing any API, verify it against the real source at
`/home/elie-gambache/IdeaProjects/Nucleus/<module>/src/main/kotlin/...`.

1. Trust `.nucleus-inventory.md` for the shape, but it may be **stale** — the source is truth.
2. If the existing page references a type, function, or artifact that is **not** in the source,
   correct it or remove it. Note the removal in your summary.
3. Never invent APIs. If unsure a symbol exists, grep for it before documenting it.
4. Match signatures exactly: enum values, function names, DSL property names.

## 9. Cross-links

- Absolute `/docs/...` paths to the **English** slug; Fumadocs i18n resolves to the current
  language. Example: `[window state](/docs/windows/window-state)`.
- Every page ends with `## What's next` linking 2–4 related pages.

## 9b. Changelog deep-links (required for every documented release)

When a release changes documented behavior, the changelog entry **must** deep-link to the
docs that describe it. Do **not** add sidebar "New" badges or marketing chips — the changelog
is the index of what is new.

Rules for agents and humans writing `content/docs/changelog.mdx` (+ `.fr.mdx`):

1. **Every user-facing feature / API / task change** that has a docs page ends with
   `See [label](/docs/<path>#<heading-slug>)` (or `Voir …` on the French page).
2. Prefer **section anchors**, not only the page root:
   - Page: `/docs/windows/window-scaffold`
   - Section: `/docs/windows/window-scaffold#chrome-primitives`
3. Derive the anchor from the **heading text of that language's page** (Fumadocs / rehype-slug):
   - EN: `## Choose a garbage collector` → `#choose-a-garbage-collector`
   - FR: `## Choisir un garbage collector` → `#choisir-un-garbage-collector`
   - Lowercase, spaces → `-`, strip most punctuation; keep accents if the FR heading has them.
4. French changelog (`.fr.mdx`) uses **French labels** and **French heading anchors** on the
   same English path (`/docs/...` — locale is applied by the site).
5. Pure internal fixes with no public docs (CI-only, hot-reload gate name, etc.) need no link.
6. When you add or rewrite docs for a release, update the matching changelog bullets in the
   **same change** so links never point at missing sections.
7. Do **not** invent sidebar badges, "NEW" menu labels, or similar UI chrome for new pages.
8. **Verify anchors against the built HTML, never against the Markdown.** Run
   `npm run build && npm run check-links` — it reads the real `id` attributes out of
   `.next/server/app`. Do not hand-derive a slug: `github-slugger` turns *every single space*
   into its own dash, so `## \`graalvm { }\` reference` is `#graalvm---reference`, not
   `#graalvm-reference`. A checker that collapses whitespace reports correct anchors as broken and
   "fixes" them into dead ones.

Example (EN):

```md
- **`WindowScaffold` + `TitleBarPlacement`** (#412) — … See
  [title bar placement](/docs/windows/window-scaffold#title-bar-placement).
- **Scheme-only deep link URIs** (#414) — … See
  [Deep links — how it works](/docs/lifecycle/deep-links#how-it-works).
```

## 10. French pages

- Same file, `.fr.mdx` suffix, same folder, same `meta.json` order.
  If the slug contains a dot (`from-1.x`), the English file must be `{slug}.en.mdx` — a bare
  `{slug}.mdx` is parsed as locale `x` and 404s.
- Vouvoiement. Translate prose, headings, callout titles/bodies, and descriptions.
- **Do not translate identifiers** — class, function, property, enum, artifact names stay English.
- Translate headings to imperative French: `Add the dependency` → `Ajouter la dépendance`,
  `Run the app` → `Lancer l'application`, `Package the app` → `Empaqueter l'application`,
  `Under the hood` → `En coulisses`, `Notes` → `Notes`, `What's next` → `Et ensuite`,
  `Before you start` → `Avant de commencer`, `API reference` → `Référence de l'API`.
- Reshape sentences to read naturally in French — never word-for-word translate.

## 11. Anti-patterns (reject on sight)

- `## TL;DR` blocks.
- Marketing ledes / hype adjectives (see §1 ban list).
- Long preamble before the first code snippet on a procedural page.
- Documenting APIs not present in the source.
- Emojis in body text.
- "Welcome to the docs!" filler.
- Title Case headings.
- Translating identifier names into French.

## Worked example: `start/quickstart.mdx`

This is the gold standard. Every conversion should feel like this.

````mdx
---
title: Quickstart
description: Build and run your first Nucleus desktop app, then package it as a native installer.
---

import { Callout } from 'fumadocs-ui/components/callout';

In this tutorial, you'll create a Nucleus desktop app from scratch, run it in a native window, and
package it as an installer for your current operating system. The app takes two files: a Gradle
build script and a Kotlin `main` function.

## Before you start

You need:

- **JDK 17 or later** on your `PATH`.
- **Kotlin 2.4.20 or later** and **Gradle 9.0 or later**.

See [Install](/docs/start/install#compatibility) for the version table.

## Create the build script

In an empty project directory, create `build.gradle.kts`:

```kotlin title="build.gradle.kts"
import dev.nucleusframework.desktop.application.dsl.TargetFormat

plugins {
    kotlin("jvm") version "2.4.20"
    kotlin("plugin.compose") version "2.4.20"
    id("org.jetbrains.compose") version "1.12.1"
    id("dev.nucleusframework") version "<version>"
}

repositories {
    mavenCentral()
    google()
}

dependencies {
    implementation(compose.desktop.currentOs)
    // Entry point: nucleusApplication, DecoratedWindow, and the native window runtime
    implementation("dev.nucleusframework:nucleus.nucleus-application:<version>")
}

nucleus.application {
    mainClass = "com.example.MainKt"

    nativeDistributions {
        packageName = "MyApp"
        packageVersion = "1.0.0"
        targetFormats(TargetFormat.Dmg, TargetFormat.Msi, TargetFormat.Deb)
    }
}
```

`nucleus-application` is the only Nucleus dependency the app needs. It brings the window runtime,
the dark-mode detector, and the GraalVM and AOT runtime support with it.

Already have a Compose Desktop app? Rename the application block and keep its content:

```diff
-compose.desktop.application {
+nucleus.application {
     mainClass = "com.example.MainKt"
     // nativeDistributions { ... } stays the same
 }
```

The entry point changes too: `application { Window(...) }` becomes
`nucleusApplication { DecoratedWindow(...) }`. See [Migrate from JetBrains Compose Desktop](/docs/migrate/from-jb-compose).

## Write the application

Create `src/main/kotlin/com/example/Main.kt`:

```kotlin title="Main.kt"
package com.example

import androidx.compose.foundation.layout.Box
import androidx.compose.foundation.layout.fillMaxSize
import androidx.compose.material.Text
import androidx.compose.ui.Modifier
import dev.nucleusframework.application.DecoratedWindow
import dev.nucleusframework.application.nucleusApplication

fun main(args: Array<String>) = nucleusApplication(args) {
    DecoratedWindow(
        onCloseRequest = ::exitApplication,
        title = "MyApp",
    ) {
        Box(Modifier.fillMaxSize()) {
            Text("Hello from Nucleus")
        }
    }
}
```

`nucleusApplication` starts the Nucleus runtime and its native event loop, which also serves as
`Dispatchers.Main`. `DecoratedWindow` opens a Compose window with a native title bar. Pass the
process `args` so deep links and file associations reach the app.

<Callout type="warn" title="Changed in 3.0">
`nucleusApplication` has no `backend` parameter, and `NucleusBackend` no longer exists. Compose
Desktop's `Window`, `Dialog`, and `Tray` are unsupported inside it. See
[Migrate from Nucleus 2.x](/docs/migrate/from-2.x).
</Callout>

## Run the app

```shell
./gradlew run
```

A window opens with a custom title bar. Nucleus draws the window controls on Linux and Windows;
on macOS the system draws the traffic lights.

## Package the app

```shell
./gradlew packageDistributionForCurrentOS
```

The plugin writes the installer to `build/compose/binaries/main/<format>/`: a `.dmg` on macOS, an
`.msi` on Windows, and a `.deb` on Linux. Add formats with `targetFormats(...)`. See
[Configuration](/docs/start/configuration#select-packaging-formats).

- [Windows](/docs/windows): `DecoratedWindow`, title bars, and dialogs.
- [Configuration](/docs/start/configuration): the `nucleus { }` DSL.
- [Architecture](/docs/concepts/architecture): what runs under your `main` function.
````

Note what changed from the original: the marketing lede and `## TL;DR` are gone; headings are
task-imperative; shell blocks use `shell`; the closer is `## What's next`. The facts (APIs,
coordinates, tasks) were preserved — but still verify them against the source per §8.
