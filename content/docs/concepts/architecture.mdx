A Nucleus app is a Compose Multiplatform app. Nucleus adds native windows and OS integration
underneath it, and the Gradle plugin packages the result. `DecoratedWindow` and helpers such as
`isSystemInDarkMode()` are regular `@Composable` functions.

## The layers

| Layer | What it contains |
|---|---|
| Your application | Compose UI and business logic, shareable with Android and iOS through `commonMain`. |
| Nucleus runtime | OS integration, lifecycle, performance and update modules, and `nucleusApplication`. See [Modules](/docs/concepts/modules). |
| Window layer | Native windows, input and the event loop. `nucleus-application` brings it in. |
| Compose Multiplatform | The UI toolkit. |
| Runtime | A JVM (JDK 17 or later, any vendor; JDK 25 with `decorated-window-jewel`) or a GraalVM native image. See [Runtimes](/docs/performance). |

`nucleusApplication` runs the event loop on the calling thread and returns once the last window
closes. Input, composition and drawing share one thread; see [Threading](/docs/concepts/threading).

<Callout type="warn" title="Changed in 3.0">
The AWT backends (`decorated-window-awt`, `-jbr`, `-jni`), `NucleusBackend` and the `backend =`
argument are gone. Compose Desktop's AWT `Window`, `Dialog` and `Tray` are unsupported. See
[Migrate from 2.x](/docs/migrate/from-2.x).
</Callout>

## Where AWT still runs

- Compose starts the AWT event thread, which keeps the JVM alive. `nucleusApplication` therefore
  calls `exitProcess` after the last window closes. Pass `exitProcessOnExit = false` to return
  and keep running.
- Your own AWT code runs on the AWT event thread, a different thread from the one Compose uses.
- A Swing or Compose Desktop host that embeds Nucleus libraries without `nucleusApplication` still
  works. Check `WindowBackend.Current` to tell the cases apart:

```kotlin
if (WindowBackend.Current == WindowBackend.Tao) {
    // Launched through nucleusApplication
}
```

## Native libraries

Nucleus loads its JNI libraries for you. In `./gradlew run`, IDE runs and fat JARs, it extracts
them to a per-user cache; relocate it with `-Dnucleus.native.cacheDir=<dir>`. See
[Native library loader](/docs/performance/native-library-loader).

<Callout type="warn" title="Changed in 3.0">
Packaged apps no longer carry Nucleus native libraries inside their JARs. Code that read them as
classpath resources must load them through `NativeLibraryLoader`.
</Callout>

<Accordions>
<Accordion title="Under the hood">

- The window layer is `decorated-window-tao`, a wrapper around Tao, a Rust windowing library.
- Most runtime modules compile to Java 11 bytecode, so libraries that embed them work on older
  toolchains.
- Skia draws through Metal on macOS, ANGLE on Direct3D 11 on Windows, and EGL on Linux.
- Packaged JVM apps load native libraries from the app directory (`-Dnucleus.native.libraryPath`),
  native images from next to the executable.
- In an AWT host, `WindowBackend.Current` is `WindowBackend.Awt` and native callbacks run on the
  AWT event thread.

</Accordion>
