Dans ce tutoriel, vous allez porter une application Nucleus 2.x vers 3.0. Corrigez d'abord les
erreurs de compilation, puis passez en revue les changements d'exécution et de build qui modifient
le comportement sans casser la compilation.

## Avant de commencer

- Passez le plugin et chaque artefact `dev.nucleusframework` en `<version>`.
- Utilisez JDK 17 ou plus récent et Compose Multiplatform 1.12. Voir
  [Compatibilité](/docs/start/install).
- Si votre application utilise `decorated-window-jbr` ou `decorated-window-jni`, prévoyez du temps
  pour [retirer AWT](#remplacer-les-fenêtres-dialogues-et-tray-de-compose-desktop). C'est l'étape
  la plus longue.

## Supprimer la sélection du backend

Tao est le seul runtime de fenêtres de 3.0, et `nucleus-application` l'apporte avec lui.

1. Retirez `decorated-window-jbr`, `decorated-window-jni`, `decorated-window-awt` et
   `decorated-window-tao` des dépendances de chaque module.
2. Retirez l'argument `backend` et l'import de `NucleusBackend`. Supprimez les lectures de
   `LocalNucleusBackend` et de `NucleusApplicationScope.backend`, et gardez la branche Tao du code
   propre à un backend :

   ```diff
   -fun main(args: Array<String>) = nucleusApplication(args, backend = NucleusBackend.Tao) {
   +fun main(args: Array<String>) = nucleusApplication(args) {
   ```

3. Remplacez `nucleusWindow.unsafe.awtWindow` par `unsafe.taoWindow`, ou `unsafe.taoHandle` pour le
   handle natif. Regardez d'abord `NucleusWindow` : `toFront()`, `setMinimumSize()`, `setIcon()` et
   `boundsOnScreen()` couvrent la plupart des appels.
4. Appelez les fenêtres et dialogues Material et Jewel sur un `NucleusApplicationScope` : les
   surcharges AWT sans receveur ont disparu. Dans `nucleusApplication { }`, rien ne change. Plus bas
   dans la composition, lisez le scope dans `LocalNucleusApplicationScope` :

   ```kotlin
   val scope = LocalNucleusApplicationScope.current
   scope.MaterialDecoratedWindow(onCloseRequest = onClose, title = "Editor") { EditorContent() }
   ```

## Remplacer les fenêtres, dialogues et tray de Compose Desktop

Nucleus 3.0 ne crée jamais de fenêtre AWT : `Window`, `DialogWindow` et `Tray` de Compose Desktop
échouent donc sous `nucleusApplication`. Remplacez chacun par son équivalent Nucleus :

| Compose Desktop (AWT) | Nucleus 3.0 |
| --- | --- |
| `Window(…)` | `DecoratedWindow(…)`, ou `HostedWindow(…)` dans une bibliothèque |
| `DialogWindow(…)` | `DecoratedDialog(…)`, ou `HostedDialog(…)` dans une bibliothèque |
| `Tray(…)` de `androidx.compose.ui.window` | `Tray(…)` de [ComposeNativeTray](/docs/os/tray) |
| `SwingPanel`, `Canvas` AWT | [`NativeView`](/docs/native-content/native-views) |
| `JFileChooser`, `java.awt.FileDialog` | [FileKit](/docs/os/file-dialogs) |
| `window.window` (`ComposeWindow`) | `nucleusWindow` et `LocalNucleusWindow` |

`DecoratedWindow` et `DecoratedDialog` prennent les mêmes arguments `onCloseRequest` et `title`.
`HostedWindow` et `HostedDialog` prennent le toolkit fourni par l'application : une bibliothèque
n'impose donc pas d'apparence.

Pour le tray, ajoutez `dev.nucleusframework:composenativetray:<version>` et importez
`dev.nucleusframework.composenativetray.tray.api.Tray`. Son API diffère du `Tray` de Compose :
portez le menu avec le [DSL de menu du tray](/docs/os/tray/menu).

<Callout type="info">
Les classes AWT qui n'ont pas besoin de fenêtre continuent de fonctionner : `BufferedImage`,
`ImageIO`, `java.awt.Font` et le presse-papiers AWT. Les API qui exigent une fenêtre ou la boucle
d'événements AWT ne fonctionnent pas.
</Callout>

## Passer l'état de fenêtre au package v2 de Nucleus

L'API de fenêtres v2 de Compose 1.12 dépend d'AWT : Nucleus en livre une copie aux mêmes membres.
Changez l'import de `rememberWindowState`, `WindowState`, `DialogState`, `Screen`, des fournisseurs
de géométrie et des fabriques `remember*` :

```diff
-import androidx.compose.ui.window.v2.rememberWindowState
+import dev.nucleusframework.window.tao.v2.rememberWindowState
```

Le `androidx.compose.ui.window.WindowState` v1 continue de fonctionner. Voir
[État de fenêtre](/docs/windows/window-state).

## Mettre à jour les hôtes de fenêtre personnalisés

`NucleusWindowHost.Window` prend `minimizable: Boolean` et `maximizable: Boolean` après
`resizable`. Un hôte thématisé doit ajouter les deux et les transmettre. Ils valent `true` par
défaut sur `DecoratedWindow` et `HostedWindow`, et `DecoratedDialog` passe `false`.
`NucleusDialogHost` ne change pas.

## Activer les API multifenêtres

Les satellites, le dock et les onglets sont `@ExperimentalNucleusApi` au niveau `ERROR`. Activez-les
par site d'appel ou par module :

```kotlin title="build.gradle.kts"
kotlin {
    compilerOptions {
        optIn.add("dev.nucleusframework.window.ExperimentalNucleusApi")
    }
}
```

Si vous utilisiez une pré-version, renommez `SatelliteDragKind` en `WorkspaceDragKind` (il sert
désormais les deux workspaces) et `dropGhost.title` en `dropGhost.tab.title`.

Sous Wayland natif, l'application ne peut ni lire ni fixer la position des fenêtres à l'écran.
Testez `TaoWindow.canPlaceOnScreen` (ou `SatelliteScope.isCompositorPlaced` dans un satellite),
pas le nom du compositeur. Voir [Linux et Wayland](/docs/windows/linux-wayland).

## Remplacer les options store du PKG

Un PKG cible désormais soit le Mac App Store, soit Developer ID. Déplacez l'option dans le bloc
`pkg { }` :

```diff title="build.gradle.kts"
 macOS {
-    appStore = true
+    pkg { appStore = true } // default; false builds a Developer ID PKG
 }
```

Dans le code, remplacez les tests `ExecutableRuntime.isPkg()` et `isStoreFormat` par
`ExecutableRuntime.isSandboxed()`. Un PKG Developer ID n'est pas sandboxé et peut donc se mettre à
jour. Voir [Sandboxing](/docs/packaging/sandboxing).

## Passer en revue les changements de comportement

Ces changements compilent sans erreur. Vérifiez chacun sur votre application.

### Vérifier vos gestionnaires de fermeture

Sous macOS, Cmd+Q et Dock → Quitter appellent désormais `onCloseRequest` sur chaque fenêtre
ouverte, comme sous Windows et Linux. Un gestionnaire qui n'appelle pas `exitApplication()` et ne
ferme pas sa fenêtre annule la sortie. Un gestionnaire qui masque dans le tray laisse passer la
sortie tant que `NucleusApplicationScope.isQuitting` vaut `true`. Voir
[Application](/docs/lifecycle/application).

### Sortir les callbacks natifs de l'EDT AWT

Les callbacks de `notification-linux`, `notification-windows`, `media-control`, `launcher-linux`
et `launcher-macos` s'exécutent sur le thread UI de l'hôte. Les écritures d'état Compose
fonctionnent toujours. Retirez-en les tests `SwingUtilities.isEventDispatchThread()` et les appels
Swing. Voir [Threading](/docs/concepts/threading).

### Gérer les événements de pincement et de pan

Un pincement au trackpad ou Ctrl+molette arrive en `ScaleStart` / `ScaleChange` / `ScaleEnd`, que
`detectTransformGestures` ne voit pas en Compose 1.12 : utilisez `Modifier.transformable`. Sous
macOS, le défilement au trackpad arrive en `PanStart` / `PanMove` / `PanEnd`. `Modifier.scrollable`
le gère, mais un gestionnaire `Scroll` personnalisé doit aussi gérer Pan :

```kotlin
when (event.type) {
    PointerEventType.Scroll -> offset += change.scrollDelta * stepPx
    PointerEventType.PanMove -> offset += change.panOffset
    PointerEventType.ScaleChange -> zoom *= change.scaleFactor
}
```

`-Dnucleus.tao.trackpadPanEvents=false` envoie le défilement au trackpad en `Scroll`. Voir
[Gestes du trackpad](/docs/input/trackpad-gestures).

### Tester l'instance unique en développement

Un second `./gradlew run` ou lancement depuis l'IDE démarre désormais une instance séparée. Les
builds empaquetés gardent le verrou. Pour tester la redirection depuis `run`, passez
`nucleusApplication(args, enableSingleInstance = true)`.

### Vérifier l'initialisation de FileKit

Quand FileKit est sur le classpath, `nucleusApplication` appelle `FileKit.init(NucleusApp.appId)` :
lancements de développement, applications empaquetées et images natives partagent un même
répertoire de données. Un appel à `FileKit.init` avant `nucleusApplication` garde votre
configuration. Passez `initializeFileKit = false` pour ne pas toucher à FileKit.

### Gérer le watchdog de la boucle d'événements

Sous Windows, une boucle d'événements bloquée journalise désormais `SEVERE` avec un dump des
threads. Affichez votre propre UI depuis les callbacks, et encadrez le travail synchrone long connu
pour qu'il ne soit pas signalé :

```kotlin
nucleusApplication(args) {
    onUnresponsive { showWaitOrQuit() }
    onResponsive { hideWaitOrQuit() }
    expectUnresponsive { importHugeProjectSynchronously() }
}
```

`-Dnucleus.tao.watchdog=false` désactive le watchdog.

### Vérifier le texte LCD sous Windows

Sous Windows, les fenêtres opaques rendent désormais le texte en antialiasing ClearType, ce qui
change les captures. Mettez à jour vos références, ou désactivez-le avec `-Dnucleus.text.lcd=false`
à l'exécution ou `-Pnucleus.text.lcd.patch=false` au build.

### Conserver les polices du JRE pour le texte AWT

L'image runtime jlink ne contient plus les polices du JRE, car Compose dessine avec les siennes. Si
vous rendez du texte via AWT ou Swing, écrivez `stripJreFonts = false` dans `nativeDistributions`.

### Charger les bibliothèques natives Nucleus via le loader

Les applications empaquetées placent les bibliothèques JNI de Nucleus à côté de l'application, plus
dans les JAR des modules. Le code qui les lisait comme ressources JAR doit appeler
`NativeLibraryLoader.load(…)`. Vos propres bibliothèques sous `nucleus/native/` restent dans leurs
JAR.

## Mettre à jour le build et la CI

### Retirer Node.js de la CI

Le plugin télécharge le Node.js dont le packaging a besoin. Retirez `actions/setup-node` de vos
workflows et ajoutez `~/.gradle/nucleus/nodejs` aux chemins mis en cache. Pour garder le `node` du
`PATH`, écrivez `nodejs { autoDownload = false }` dans `nativeDistributions`. Voir
[CI/CD](/docs/packaging/ci-cd).

### Activer le pack de démarrage

`nucleusOptimization` est désactivé par défaut. Un seul interrupteur active Serial GC, un tas
compact, un JAR runtime unique, le GC au repos et `lastJdk` (OpenJDK 27). Surchargez un réglage
dans le bloc :

```kotlin title="build.gradle.kts"
nucleus.application {
    nucleusOptimization = true
    nucleusOptimization { lastJdk = false }
}
```

Un `javaHome` explicite l'emporte sur `lastJdk`. Voir [Performance](/docs/performance).

## Retester l'application

Lancez l'application, puis testez chaque intégration qui dépendait d'AWT :

- **Glisser-déposer.** Réécrivez les gestionnaires qui lisaient des données `TransferHandler` AWT.
  Voir [Glisser-déposer](/docs/input/drag-and-drop).
- **Liens profonds.** `onDeepLink { uri -> … }` ne change pas.
- **Dialogues de fichiers et vues embarquées.** Vérifiez chaque sélecteur FileKit et chaque
  `NativeView`.
- **Placement des fenêtres sous Linux.** Les compositeurs Wayland ignorent les positions absolues.
- **La sortie de l'application** sous macOS, et chaque gestionnaire de fermeture.
- **Le packaging.** Construisez une fois chaque format d'installeur, et une image native si vous en
  livrez une.
