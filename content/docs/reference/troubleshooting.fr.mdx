Cette page recense les problèmes récurrents quand vous compilez, empaquetez, signez et lancez
une application Nucleus. Les entrées sont regroupées par domaine, et chacune donne le
symptôme, la cause et la solution.

## Signature et notarisation macOS

### La notarisation échoue : "does not include a secure timestamp"

**Symptôme.** `xcrun notarytool submit` retourne `Invalid` avec un détail de statut
mentionnant un timestamp manquant ou invalide.

**Cause.** La signature s'est faite sans `--timestamp`, ou la machine n'a pas pu joindre
le serveur de timestamp d'Apple au moment de signer.

**Solution.** Nucleus signe avec `--options runtime --timestamp` par défaut. Si vous avez
ajouté une étape `codesign` personnalisée (par exemple pour signer des binaires universels
fusionnés avec `lipo` en dehors de l'action `build-macos-universal`), passez `--timestamp`
et re-signez. Vérifiez avec `codesign -dv --verbose=4 <Your.app>` et cherchez une entrée
`Timestamp=`.

### La notarisation échoue : "does not include a hardened runtime"

**Symptôme.** `Status: Invalid`, avec un log qui mentionne le hardened runtime.

**Cause.** Une étape `codesign` personnalisée sans `--options runtime`.

**Solution.** Ajoutez `--options runtime` à chaque invocation de `codesign`. Le pipeline
Nucleus par défaut le fait déjà, donc seuls les scripts CI personnalisés rencontrent cette
erreur.

### La notarisation échoue : "code object is not signed at all"

**Symptôme.** `packageGraalvmDmg` (ou `notarizeGraalvmDmg`) avec
`compose.desktop.mac.sign=true` aborte sur `code object is not signed at all` pour le
sous-composant `<App>.app/Contents/MacOS/.nucleus-executable-type`. Ou le bundle est
notarisé, mais `spctl -a -t exec` répond simplement `rejected`.

**Cause.** Avant 2.5.17, les bundles GraalVM plaçaient des fichiers non-code sous
`Contents/MacOS/` : le marqueur de type d'exécutable et `lib/fontconfig.bfc`. `codesign`
traite chaque fichier de ce dossier comme du code imbriqué, et Gatekeeper rejette les
fichiers non Mach-O n'importe où sous `Contents/MacOS/`. Les dylibs GraalVM qui s'y
trouvent gardaient aussi leur signature ad hoc.

**Solution.** Passez à 2.5.17 ou plus récent. Le marqueur et `fontconfig.bfc` vivent
maintenant dans `Contents/Resources/`, et chaque dylib sous `Contents/MacOS/` est re-signée
avec votre Developer ID. Les fichiers ajoutés via `appResourcesRootDir` atterrissent
toujours dans `Contents/MacOS/` sous macOS. N'y livrez que des binaires Mach-O, sinon
Gatekeeper rejette le bundle notarisé de la même façon.

## Microsoft Store

### Upload rejeté : "MinVersion &lt;= 10.0.17134.0"

**Symptôme.** Partner Center rejette l'upload :

> Package acceptance validation error: bundle is not valid. You can't upload
> msix/msixbundle/msixupload packages that target Windows with a
> MinVersion &lt;= 10.0.17134.0.

**Cause.** Aucun `minVersion` explicite n'est défini dans `appx { }`. Le défaut est
`10.0.14316.0`, en dessous du plancher du Store.

**Solution.** Définissez un `minVersion` au niveau du plancher du Store ou au-dessus :

```kotlin title="build.gradle.kts"
appx {
    minVersion = "10.0.17763.0"        // Windows 10 1809
    maxVersionTested = "10.0.22621.0"  // Windows 11 22H2
}
```

### Upload rejeté : publisher ou identité incohérents

**Symptôme.** La validation de l'upload échoue avec une incohérence d'identité.

**Cause.** `identityName`, `publisher` ou `publisherDisplayName` ne correspondent pas à la
réservation Partner Center.

**Solution.** Recopiez les valeurs exactes depuis Partner Center, sous Product identity.
`publisher` est le `CN=<GUID>` émis par le Store, pas le CN de votre certificat de signature
local. Voir [cibles Windows](/docs/packaging/windows).

## Réseau

### SSLHandshakeException sur un réseau d'entreprise

**Symptôme.** Les appels HTTPS de l'application échouent avec
`SSLHandshakeException: PKIX path building failed`.

**Cause.** Un proxy d'entreprise ou une passerelle VPN intercepte le TLS avec une CA
racine privée que le trust store du JDK embarqué ne connaît pas.

**Solution.** Utilisez l'une des deux approches, ou les deux.

Livrez la CA dans le `cacerts` du JDK embarqué au moment du build :

```kotlin title="build.gradle.kts"
nativeDistributions {
    trustedCertificates.from(files("certs/corp-ca.pem"))
}
```

Voir [certificats de confiance](/docs/packaging/trusted-certificates).

Ou routez le HTTPS via le trust store de l'OS à l'exécution, avec `native-ssl` et
`native-http` :

```kotlin title="build.gradle.kts"
implementation("dev.nucleusframework:nucleus.native-ssl:<version>")
implementation("dev.nucleusframework:nucleus.native-http:<version>")
```

`NativeHttpClient.create()` retourne un `java.net.http.HttpClient` adossé au trust store de
l'OS. Pour OkHttp ou Ktor, utilisez les intégrations `nucleus.native-http-okhttp` et
`nucleus.native-http-ktor`.

## Auto-update

### "no matching file" sur macOS

**Symptôme.** Une vérification retourne un `UpdateResult.Error` encapsulant une
`NoMatchingFileException` sur macOS.

**Cause.** La release ne contient qu'un `.dmg`. L'auto-update sur macOS télécharge un ZIP.

**Solution.** Ajoutez `TargetFormat.Zip` à côté de `TargetFormat.Dmg`. Les deux vont dans
la même release, et `latest-mac.yml` référence les deux. Voir
[auto-update](/docs/packaging/auto-update).

## GraalVM native image

### ClassNotFoundException ou NoSuchMethodError à l'exécution

**Symptôme.** L'application tourne sur la JVM mais plante sous `native-image` avec des
erreurs de réflexion ou des méthodes manquantes.

**Cause.** GraalVM procède par analyse en monde fermé. La réflexion, les ressources et les
proxies dynamiques doivent être enregistrés à l'avance.

**Solution.** Le plugin Nucleus fournit des métadonnées de reachability GraalVM pour
lui-même, FileKit et d'autres bibliothèques courantes (voir
[métadonnées automatiques](/docs/performance/graalvm/automatic-metadata)). Pour votre propre
code :

1. Lancez l'application avec `-agentlib:native-image-agent=config-output-dir=...` sur une
   charge de travail représentative.
2. Committez le `reachability-metadata.json` généré à côté de `META-INF/native-image/`.

Pour les bibliothèques non prises en charge, voir
[configuration GraalVM](/docs/performance/graalvm/configuration).

## Packaging

### Le téléchargement de Node.js échoue pendant le packaging

**Symptôme.** Une tâche `package*` logue `Could not provision Node.js (…) — falling back to the
one on PATH`, puis échoue avec `node not found. Node.js 18+ is required for electron-builder
packaging`.

**Cause.** electron-builder tourne sur Node.js, que le plugin télécharge depuis `nodejs.org` au
premier usage. La machine de build est hors ligne ou un proxy bloque le téléchargement, et aucun
`node` ne se trouve non plus sur le `PATH`. Le plugin choisit Node.js dans cet ordre :

1. La propriété Gradle `compose.electronBuilder.nodePath` (le binaire `node` ou son dossier).
2. La variable d'environnement `NUCLEUS_NODE_HOME`.
3. L'installation que le plugin provisionne depuis `nativeDistributions { nodejs { } }`.
4. `node` sur le `PATH`, utilisé quand `autoDownload` vaut `false` ou quand le téléchargement
   échoue.

**Solution.** Indiquez une installation locale avec la propriété Gradle ou `NUCLEUS_NODE_HOME`.
Pour utiliser le `node` du `PATH` sans tenter de téléchargement, désactivez le provisionnement :

```kotlin title="build.gradle.kts"
nativeDistributions {
    nodejs {
        autoDownload = false
    }
}
```

Voir [Provisionner Node.js](/docs/packaging#provisionner-nodejs).

## Packaging Linux

### L'AppImage met environ 60 secondes à démarrer

**Symptôme.** L'application s'ouvre rapidement en développement mais prend près d'une
minute une fois packagée en AppImage.

**Cause.** `compressionLevel = CompressionLevel.Maximum` ou `Ultra`. L'AppImage utilise squashfs, et
la compression maximale déclenche une décompression FUSE à chaque lancement.

**Solution.** Utilisez `CompressionLevel.Normal` (le défaut) pour AppImage. Préférez une
surcharge par format pour garder DEB/DMG sur un niveau global plus élevé :

```kotlin title="build.gradle.kts"
nativeDistributions {
    compressionLevel = CompressionLevel.Ultra
    linux {
        appImage {
            compressionLevel = CompressionLevel.Normal
        }
    }
}
```

### DEB ou RPM échoue : "Please specify project homepage"

**Symptôme.** `packageDeb` ou `packageGraalvmDeb` échoue immédiatement.

**Cause.** Contrairement à jpackage, electron-builder exige `homepage` pour DEB.

**Solution.** Définissez la homepage sur la distribution :

```kotlin title="build.gradle.kts"
nativeDistributions {
    homepage = "https://myapp.example.com"
}
```

### La tâche Flatpak est ignorée silencieusement

**Symptôme.** `packageFlatpak` rapporte "skipped" sans erreur.

**Cause.** `flatpak-builder` ou le runtime `org.freedesktop.Platform//23.08` manque sur
l'hôte de build.

**Solution.** Installez les outils et le runtime :

```shell
sudo apt-get install -y flatpak flatpak-builder
flatpak remote-add --if-not-exists flathub https://flathub.org/repo/flathub.flatpakrepo
flatpak install -y flathub org.freedesktop.Platform//23.08
flatpak install -y flathub org.freedesktop.Sdk//23.08
```

En CI, utilisez `setup-nucleus` avec `flatpak: 'true'`.

### Snap échoue : "snapcraft: command not found"

**Symptôme.** `packageSnap` échoue avant de produire quoi que ce soit.

**Cause.** `snapd` ou `snapcraft` manque sur l'hôte de build.

**Solution.** Installez les deux :

```shell
sudo apt-get install -y snapd
sudo snap install snapcraft --classic
```

En CI, utilisez `setup-nucleus` avec `snap: 'true'`.

## Bibliothèques natives

### Le module rapporte `isAvailable == false` ou des no-ops silencieux

**Symptôme.** Le system tray, la couleur système, les notifications ou un autre module
d'intégration OS ne fait rien sur une plateforme où vous l'attendez. Les APIs publiques
renvoient `null` / `false`, ou `isAvailable` vaut `false`.

**Cause.** La bibliothèque partagée JNI de ce module n'a pas chargé. Raisons courantes :
pas de binaire pour cet OS/arch dans le JAR de la dépendance, module absent du classpath
runtime, ou échec d'extraction dans le cache adressé par contenu.

**Solution.** Vérifiez que la dépendance du module est sur le classpath runtime et que le
JAR contient `/nucleus/native/<os>-<arch>/…` pour votre plateforme. Videz le cache du
chargeur et relancez si une montée de version a laissé une extraction partielle :

| Plateforme | Chemin de cache |
|------------|-----------------|
| macOS | `~/Library/Caches/nucleus/native/` |
| Linux | `~/.cache/nucleus/native/` (ou `$XDG_CACHE_HOME/nucleus/native/`) |
| Windows | `%LOCALAPPDATA%\nucleus\native\` |

Voir le [chargeur de bibliothèques natives](/docs/performance/native-library-loader) pour
l'ordre de chargement, la disposition JAR et les règles de sidecars.

### Une bibliothèque native ne se charge pas sur une distribution Linux ancienne

**Symptôme.** Sur Ubuntu 22.04, Debian 12, Devuan 5 ou une autre distribution antérieure à
Ubuntu 24.04, l'app crashe au lancement ou un module rapporte `isAvailable == false`.
stderr affiche `version 'GLIBC_2.3x' not found` pour une bibliothèque `libnucleus_*.so`.

**Cause.** Jusqu'à 2.5.17, les natives Linux étaient compilées sur `ubuntu-latest`
(Ubuntu 24.04) et exigeaient donc glibc 2.39.

**Solution.** Passez à 2.5.18 ou plus récent. Les natives sont compilées sur Ubuntu 22.04
et demandent glibc 2.35 ou plus récent. Vérifiez la version de votre système avec
`ldd --version`.

## Rendu

### Crash au lancement sur un GPU Linux ancien

**Symptôme.** Une fenêtre abandonne à l'ouverture sous Linux. stderr signale un contexte GL 3.3
refusé, ou le processus quitte depuis `TaoComposeSceneHostLinux` sur un `require()` en échec.

**Cause.** Avant 2.5.16, l'attach EGL sous Linux ne demandait qu'un profil GL 3.3
**compatibility**. Certains drivers (Mesa r600 sur AMD RV610, par exemple) plafonnent le profil
compat à 3.0 alors que le profil **core** atteint 3.3. La requête ne pouvait jamais aboutir, et
la fenêtre abandonnait.

**Solution.** Passez à 2.5.16 ou plus récent. L'attach essaie 3.3 compat, puis 3.3 core, puis
Mesa llvmpipe (`LIBGL_ALWAYS_SOFTWARE=1`, une seule fois, ignoré si vous avez déjà défini cette
variable). Chaque repli écrit une ligne sur stderr. Le matériel qui accepte la requête compat se
comporte comme avant. Définissez vous-même `LIBGL_ALWAYS_SOFTWARE=1` pour forcer llvmpipe dès le
départ.

## Boucle d'événements

### Une fenêtre se fige et le log contient un thread dump

**Symptôme.** Sous Windows, une fenêtre passe en « Ne répond pas », et le log contient une
entrée `SEVERE` : `Tao event loop has not pumped messages for at least <n> ms — the UI is
frozen. Thread dump follows.`

**Cause.** Le thread UI est bloqué. Un deadlock ou un long travail synchrone empêche la boucle
d'événements de traiter ses messages. Le watchdog de la boucle le détecte et dumpe tous les
threads, celui de la boucle en premier.

**Solution.** Lisez la pile du thread de la boucle, en tête du dump, et sortez l'appel bloquant
du thread UI. Pour un travail qui doit y rester, entourez-le de `expectUnresponsive { }` : le
watchdog l'ignore. Enregistrez `onUnresponsive` pour remonter les blocages en production. Voir
[Détecter une boucle d'événements bloquée](/docs/concepts/threading#détecter-une-boucle-dévénements-bloquée).

## Saisie

### Un gestionnaire de scroll ignore le trackpad macOS

**Symptôme.** Sous macOS, un gestionnaire `pointerInput` qui réagit à `PointerEventType.Scroll`
fonctionne avec une molette, mais pas avec un balayage à deux doigts sur le trackpad.
`LazyColumn` et `Modifier.scrollable` défilent toujours.

<Callout type="warn" title="Modifié en 3.0">
Un balayage au trackpad sous macOS arrive désormais en `PanStart`, `PanMove` et `PanEnd`. En 2.x,
il arrivait en `Scroll`. Voir [Migrer depuis 2.x](/docs/migrate/from-2.x).
</Callout>

**Cause.** Votre gestionnaire n'écoute que `Scroll` et ne voit donc jamais les événements de pan.

**Solution.** Traitez `PointerEventType.PanMove` et lisez `change.panOffset` à côté de votre
branche `Scroll`. Pour recevoir de nouveau chaque pas du trackpad en `Scroll`, lancez la JVM avec
`-Dnucleus.tao.trackpadPanEvents=false`. Voir
[Défiler au trackpad sur macOS](/docs/input/trackpad-gestures#défiler).

### Le pincement n'atteint plus detectTransformGestures

**Symptôme.** Un pincement sur le trackpad ne zoome plus un contenu qui utilise
`detectTransformGestures`.

<Callout type="warn" title="Modifié en 3.0">
Un pincement arrive désormais dans Compose en `ScaleStart`, `ScaleChange` et `ScaleEnd`. En 2.x,
c'étaient deux pointeurs tactiles synthétiques. Voir [Migrer depuis 2.x](/docs/migrate/from-2.x).
</Callout>

**Cause.** `detectTransformGestures` suit des pointeurs tactiles et ne voit pas les événements
Scale.

**Solution.** Déplacez la gestion du pincement vers `Modifier.transformable` ou vers un listener
des événements `Scale*`. Voir [Zoomer par pincement](/docs/input/trackpad-gestures#zoomer-par-pincement).

## Cycle de vie de l'application

### Cmd+Q ne quitte plus l'application

**Symptôme.** Sous macOS, Cmd+Q, Dock → Quitter ou une déconnexion laisse l'application tourner.

<Callout type="warn" title="Modifié en 3.0">
Un quit système sous macOS appelle désormais `onCloseRequest` sur chaque fenêtre ouverte. En 2.x,
il terminait l'application sans rien demander. Voir [Migrer depuis 2.x](/docs/migrate/from-2.x).
</Callout>

**Cause.** L'une de vos fenêtres a un `onCloseRequest` qui n'appelle pas `exitApplication()` et
ne ferme pas la fenêtre, par exemple un gestionnaire qui la cache dans le tray. Une fenêtre qui
reste ouverte oppose son veto au quit.

**Solution.** Laissez passer un vrai quit. Testez `isQuitting` sur le scope de l'application :

```kotlin
DecoratedWindow(
    onCloseRequest = {
        if (isQuitting) exitApplication() else visible = false
    },
    visible = visible,
) { /* ... */ }
```

Voir [Gérer un quit système](/docs/lifecycle/application#gérer-un-quit-système).

### La seconde instance n'est pas transmise en dev

**Symptôme.** Sous `./gradlew run` ou un lancement depuis l'IDE, une seconde copie ouvre sa
propre fenêtre au lieu de passer ses arguments à la première.

<Callout type="warn" title="Modifié en 3.0">
`enableSingleInstance` vaut désormais `!ExecutableRuntime.isDev()` par défaut. En 2.x, il était
aussi actif en dev. Voir [Migrer depuis 2.x](/docs/migrate/from-2.x).
</Callout>

**Cause.** Le verrou d'instance unique est désactivé en dev, pour qu'une copie de debug puisse
démarrer à côté d'une copie packagée.

**Solution.** Passez `enableSingleInstance = true` à `nucleusApplication` le temps de tester la
transmission. Voir [L'activer en dev](/docs/lifecycle/single-instance#lactiver-en-dev).

## Développement

### La fenêtre Hot Reload ne s'ouvre pas sous macOS

**Symptôme.** Sous macOS, un lancement Compose Hot Reload démarre le processus, mais aucune
fenêtre n'apparaît. `./gradlew run` fonctionne.

**Cause.** La boucle d'événements des fenêtres doit tourner sur le thread 0 de macOS, et la tâche
`JavaExec` de Hot Reload ne passe pas `-XstartOnFirstThread`. Le plugin Nucleus ajoute ce flag,
mais seulement quand le projet déclare lui-même `nucleus.decorated-window-tao`. Une application
qui le reçoit via `nucleus-application` ne l'a qu'en dépendance transitive, et le plugin n'ajoute
pas le flag.

**Solution.** Déclarez la dépendance explicitement :

```kotlin title="build.gradle.kts"
implementation("dev.nucleusframework:nucleus.decorated-window-tao:<version>")
```

## Migration

### Unresolved reference: NucleusBackend

**Symptôme.** Après le passage à 3.0, la compilation échoue sur `NucleusBackend`,
`LocalNucleusBackend` ou l'argument `backend =` de `nucleusApplication`.

**Cause.** 3.0 n'a plus qu'un seul backend de fenêtres. Les modules de fenêtres AWT, JBR et JNI
sont supprimés, et l'API de sélection du backend avec eux.

**Solution.** Retirez l'import de `NucleusBackend`, l'argument `backend` et la dépendance
`decorated-window-awt`, `-jbr` ou `-jni`. Voir
[Supprimer la sélection du backend](/docs/migrate/from-2.x#supprimer-la-sélection-du-backend).

### Unresolved reference 'JewelDecoratedWindow'

**Symptôme.** L'import est correct et l'IDE résout la fonction, mais la compilation échoue.

**Cause.** `JewelDecoratedWindow` est une extension de `NucleusApplicationScope`. Un composable
wrapper sans ce receiver ne peut pas l'appeler.

**Solution.** Faites de votre wrapper une extension, lui aussi :

```kotlin
@Composable
fun NucleusApplicationScope.MyOnboardingWindow() {
    JewelDecoratedWindow(/* ... */) { /* content */ }
}
```

Voir [Migrer depuis 1.x](/docs/migrate/from-1.x).

### La dépendance Jewel ne se résout pas avec un JDK ancien

**Symptôme.** Gradle refuse l'artefact `nucleus.decorated-window-jewel` avec un message sur une
version de Java incompatible.

**Cause.** Le toolkit Jewel est compilé pour le JDK 25, et votre build cible une version plus
ancienne.

**Solution.** Réglez la toolchain JVM de Kotlin sur 25 :

```kotlin title="build.gradle.kts"
kotlin { jvmToolchain(25) }
```

Voir [Installation](/docs/start/install).
