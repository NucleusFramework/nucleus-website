Le plugin Gradle Nucleus (`id("dev.nucleusframework")`) ajoute une extension, `nucleus { }`, qui configure la tâche `run`, l'empaquetage, la signature, la publication et les images natives GraalVM. Cette page liste ses propriétés bloc par bloc, dans l'ordre des sources ; [Configuration](/docs/start/configuration) les montre dans un script de build complet.

Tous les types du DSL se trouvent dans `dev.nucleusframework.desktop.application.dsl`.

## `nucleus { }` [#nucleus]

`dev.nucleusframework.NucleusExtension` :

| Membre | Type | Notes |
| --- | --- | --- |
| `application { }` | `JvmApplication` | Application JVM : tâche `run`, empaquetage, GraalVM |
| `nativeApplication { }` | `NativeApplication` | Application Kotlin/Native macOS |
| `dependencies` | `NucleusPlugin.Dependencies` | Coordonnées des modules runtime |

### `nucleusOptimization { }` [#nucleusoptimization]

`nucleusOptimization = true` active cinq options de démarrage d'un coup. Chaque option du bloc est un `Boolean?` : `null` suit l'interrupteur principal, `true` ou `false` force l'option quelles que soient les autres.

```kotlin
nucleus.application {
    nucleusOptimization = true
    nucleusOptimization { idleGc = false }
}
```

| Option | Effet |
| --- | --- |
| `serialGc` | Serial GC quand `garbageCollector` n'est pas défini. Un collecteur explicite l'emporte |
| `compactHeap` | Ajoute `-Xms32m` et `-XX:MaxRAMPercentage=25`, sauf si `jvmArgs` les définit déjà |
| `singleJar` | Aplatit les JAR du runtime (ou active `joinOutputJars` quand ProGuard est actif) pour que l'image jpackage ne contienne qu'un JAR |
| `idleGc` | Demande un GC 3 s après la perte du focus par la dernière fenêtre, ou tout de suite quand une fenêtre est réduite. Aussi intégré aux images GraalVM |
| `lastJdk` | Empaquette et lance avec OpenJDK 27, téléchargé dans `<gradle-user-home>/nucleus/jdk` (BellSoft Liberica JDK 27 sur macOS Intel et Windows ARM). `javaHome` l'emporte. Le JDK de compilation Gradle ne change pas |

Le pack ne touche ni à `enableAotCache` ni à ProGuard. Voir [Optimisation du démarrage](/docs/performance/startup).

### `nodejs { }` [#nodejs]

`NodeJsSettings` règle le Node.js qui exécute electron-builder, dont tous les formats sauf `RawAppImage` ont besoin.

| Propriété | Type | Défaut | Notes |
| --- | --- | --- | --- |
| `autoDownload` | `Property<Boolean>` | `true` | Télécharge depuis `nodejs.org` et met en cache. `false` utilise `node` et `npm` du `PATH` |
| `version` | `Property<String>` | `"22"` | Une ligne majeure (`"22"`), `"lts"`, ou une release figée (`"22.11.0"`) |
| `installDir` | `DirectoryProperty` | `<gradle-user-home>/nucleus/nodejs` | Cache des téléchargements |

Le plugin cherche Node.js dans cet ordre : la propriété Gradle `compose.electronBuilder.nodePath`, la variable d'environnement `NUCLEUS_NODE_HOME`, ce bloc, puis le `PATH` (également utilisé si le téléchargement échoue). Une version flottante reste figée une fois téléchargée ; supprimez son répertoire sous `installDir` pour récupérer une release plus récente. Voir [Provisionner Node.js](/docs/packaging#provisionner-nodejs).

### `TargetFormat` [#targetformat]

18 formats, dans l'ordre des sources :

`RawAppImage`, `Pkg`, `Deb`, `Rpm`, `Dmg`, `Exe`, `Msi`, `Nsis`, `NsisWeb`, `Portable`, `AppX`, `AppImage`, `Pacman`, `Snap`, `Flatpak`, `Zip`, `Tar`, `SevenZ`.

jpackage construit `RawAppImage`, l'image d'application brute. electron-builder produit tous les autres formats à partir d'elle. `AppX` et `Flatpak` passent toujours par le pipeline sandboxé ; `Pkg` seulement avec `macOS { pkg { appStore = true } }`, la valeur par défaut.

<Callout type="warn" title="Modifié en 3.0">
`TargetFormat.isStoreFormat` est déprécié au niveau `ERROR` et ne compile plus. Un PKG n'est un format store que si `pkg.appStore` vaut `true` : testez donc la valeur du DSL. Voir [Migrer depuis 2.x](/docs/migrate/from-2.x).
</Callout>

### `pkg { }` [#macos-pkg]

`PkgSettings` choisit le canal de distribution du PKG.

| Propriété | Type | Défaut | Notes |
| --- | --- | --- | --- |
| `appStore` | `Boolean` | `true` | `true` : build Mac App Store, sandboxé, re-signé avec `productsign`, non notarisé. `false` : build Developer ID, même pipeline que le DMG, installeur signé avec le certificat Developer ID Installer et notarisé par `notarizePkg` |
| `preInstall` | `RegularFileProperty` | non défini | Script lancé en root avant la copie du contenu. Shebang obligatoire |
| `postInstall` | `RegularFileProperty` | non défini | Script lancé en root après la copie du contenu |

L'App Store refuse les paquets qui contiennent des scripts d'installation : le plugin échoue dès la configuration si `preInstall` ou `postInstall` est défini avec `appStore = true`. Chaque script s'exécute une seule fois par installation.

```kotlin
macOS {
    pkg {
        appStore = false
        preInstall.set(file("packaging/macos/preinstall"))
        postInstall.set(file("packaging/macos/postinstall"))
    }
}
```

Voir [Choisir un canal PKG](/docs/packaging/macos#choisir-un-canal-pkg).

### `appExtensions { }` [#macos-app-extensions]

`MacAppExtensionSettings` intègre des bundles `.appex` déjà compilés dans `Contents/PlugIns/`. Nucleus les copie et les signe, sans les construire.

| Membre | Notes |
| --- | --- |
| `extension(name) { }` | Déclare une `MacAppExtension`. `name` sert uniquement aux diagnostics |
| `appex(File)` | Le bundle `.appex` à intégrer |
| `entitlements(File)` | Entitlements de l'extension, distincts de ceux de l'application |
| `provisioningProfile(File)` | Facultatif, intégré comme `Contents/embedded.provisionprofile` dans l'extension |

```kotlin
macOS {
    appExtensions {
        extension("NetworkFilter") {
            appex(file("build/appex/NetworkFilter.appex"))
            entitlements(file("packaging/extension/NetworkExtension.entitlements"))
            provisioningProfile(file("packaging/NetworkFilter.provisionprofile"))
        }
    }
}
```

Chaque extension est signée avec ses propres entitlements, puis l'application est scellée sans `--deep`. L'extension n'existe que dans un `.app` signé : utilisez `runDistributable`, pas `run`. Voir [Intégrer des extensions d'application](/docs/packaging/macos#intégrer-des-extensions-dapplication).

### `notarization { }` [#macos-notarization]

`MacOSNotarizationSettings` accepte l'un de trois jeux d'identifiants, tous `Property<String>` :

- Apple ID : `appleID`, `password`, `teamID`

`ascProvider` est déprécié au niveau `ERROR` ; utilisez `teamID`.

## `nativeApplication { }` [#native-application]

`NativeApplication` empaquette une application Kotlin/Native. Seules les cibles macOS sont prises en charge.

## Propriétés générées de l'application [#app-properties]

Le plugin écrit `nucleus/nucleus-app.properties` dans les ressources de l'application. L'objet runtime `NucleusApp` le lit au démarrage : c'est ainsi que les valeurs du DSL parviennent aux bibliothèques runtime. Clés : `app.id`, `app.version`, `app.vendor`, `app.description`, `app.name`, `app.aumid`, `startup.wm.class`, `startup.task.id`, et `optimization.idleGc` quand l'option `idleGc` est active.
