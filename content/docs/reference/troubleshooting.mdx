This page lists recurring problems when you build, package, sign, and run a Nucleus app.
Entries are grouped by area, and each one gives the symptom, the cause, and the fix.

## macOS signing and notarization

### Notarization fails: "does not include a secure timestamp"

**Symptom.** `xcrun notarytool submit` returns `Invalid` with a status detail about a
missing or invalid timestamp.

**Cause.** Code signing ran without `--timestamp`, or the machine could not reach Apple's
timestamp server at sign time.

**Fix.** Nucleus signs with `--options runtime --timestamp` by default. If you added a
custom `codesign` step (for example, to sign `lipo`-merged universal binaries outside the
`build-macos-universal` action), pass `--timestamp` and re-sign. Verify with
`codesign -dv --verbose=4 <Your.app>` and check for a `Timestamp=` entry.

### Notarization fails: "does not include a hardened runtime"

**Symptom.** `Status: Invalid`, with the log referencing the hardened runtime.

**Cause.** A custom `codesign` step is missing `--options runtime`.

**Fix.** Add `--options runtime` to every `codesign` invocation. The default Nucleus
pipeline already does this, so only custom CI scripts hit this error.

### Notarization fails: "code object is not signed at all"

**Symptom.** `packageGraalvmDmg` (or `notarizeGraalvmDmg`) with
`compose.desktop.mac.sign=true` aborts with
`code object is not signed at all` in subcomponent
`<App>.app/Contents/MacOS/.nucleus-executable-type`. Or the bundle notarizes, but
`spctl -a -t exec` answers a bare `rejected`.

**Cause.** Before 2.5.17, GraalVM bundles put non-code files under `Contents/MacOS/`: the
executable-type marker and `lib/fontconfig.bfc`. `codesign` treats every file there as
nested code, and Gatekeeper rejects non-Mach-O files anywhere under `Contents/MacOS/`. The
GraalVM dylibs there also kept their ad-hoc signature.

**Fix.** Upgrade to 2.5.17 or later. The marker and `fontconfig.bfc` now live in
`Contents/Resources/`, and every dylib under `Contents/MacOS/` is re-signed with your
Developer ID. Files you add through `appResourcesRootDir` still land in `Contents/MacOS/`
on macOS. Ship only Mach-O binaries there, or Gatekeeper rejects the notarized bundle the
same way.

## Microsoft Store

### Upload rejected: "MinVersion &lt;= 10.0.17134.0"

**Symptom.** Partner Center rejects the upload:

> Package acceptance validation error: bundle is not valid. You can't upload
> msix/msixbundle/msixupload packages that target Windows with a
> MinVersion &lt;= 10.0.17134.0.

**Cause.** No explicit `minVersion` is set in `appx { }`. The default is `10.0.14316.0`,
which is below the Store's floor.

**Fix.** Set a `minVersion` at or above the Store's floor:

```kotlin title="build.gradle.kts"
appx {
    minVersion = "10.0.17763.0"        // Windows 10 1809
    maxVersionTested = "10.0.22621.0"  // Windows 11 22H2
}
```

### Upload rejected: publisher or identity mismatch

**Symptom.** Upload validation fails with an identity mismatch.

**Cause.** `identityName`, `publisher`, or `publisherDisplayName` do not match the Partner
Center reservation.

**Fix.** Copy the exact values from Partner Center under Product identity. `publisher` is
the `CN=<GUID>` issued by the Store, not the CN of your local signing certificate. See
[Windows targets](/docs/packaging/windows).

## Networking

### SSLHandshakeException on a corporate network

**Symptom.** HTTPS calls from the app fail with
`SSLHandshakeException: PKIX path building failed`.

**Cause.** A corporate proxy or VPN gateway intercepts TLS with a private root CA that the
bundled JDK trust store does not know.

**Fix.** Use either approach, or both.

Ship the CA inside the bundled JDK's `cacerts` at build time:

```kotlin title="build.gradle.kts"
nativeDistributions {
    trustedCertificates.from(files("certs/corp-ca.pem"))
}
```

See [trusted certificates](/docs/packaging/trusted-certificates).

Or route HTTPS through the OS trust store at runtime with `native-ssl` and `native-http`:

```kotlin title="build.gradle.kts"
implementation("dev.nucleusframework:nucleus.native-ssl:<version>")
implementation("dev.nucleusframework:nucleus.native-http:<version>")
```

`NativeHttpClient.create()` returns a `java.net.http.HttpClient` backed by the OS trust
store. For OkHttp or Ktor, use the `nucleus.native-http-okhttp` and
`nucleus.native-http-ktor` integrations.

## Auto-update

### "no matching file" on macOS

**Symptom.** A check returns `UpdateResult.Error` wrapping a `NoMatchingFileException` on
macOS.

**Cause.** The release contains only a `.dmg`. Auto-update on macOS downloads a ZIP.

**Fix.** Add `TargetFormat.Zip` alongside `TargetFormat.Dmg`. Both belong in the same
release, and `latest-mac.yml` references both. See [auto-update](/docs/packaging/auto-update).

## GraalVM native image

### ClassNotFoundException or NoSuchMethodError at runtime

**Symptom.** The app runs on the JVM but crashes under `native-image` with reflection
errors or missing methods.

**Cause.** GraalVM uses closed-world analysis. Reflection, resources, and dynamic proxies
must be registered ahead of time.

**Fix.** The Nucleus plugin ships GraalVM reachability metadata for itself, FileKit, and
other common libraries (see [automatic metadata](/docs/performance/graalvm/automatic-metadata)).
For your own code:

1. Run with `-agentlib:native-image-agent=config-output-dir=...` on a representative
   workload.
2. Commit the generated `reachability-metadata.json` next to `META-INF/native-image/`.

For unsupported libraries, see [GraalVM configuration](/docs/performance/graalvm/configuration).

## Packaging

### Node.js download fails during packaging

**Symptom.** A `package*` task logs `Could not provision Node.js (…) — falling back to the one on
PATH`, then fails with `node not found. Node.js 18+ is required for electron-builder packaging`.

**Cause.** electron-builder runs on Node.js, and the plugin downloads one from `nodejs.org` on
first use. The build host is offline or a proxy blocks the download, and no `node` sits on `PATH`
either. The plugin picks Node.js in this order:

1. The `compose.electronBuilder.nodePath` Gradle property (the `node` binary or its directory).
2. The `NUCLEUS_NODE_HOME` environment variable.
3. The installation the plugin provisions from `nativeDistributions { nodejs { } }`.
4. `node` on `PATH`, used when `autoDownload` is `false` or the download fails.

**Fix.** Point the plugin at a local install with the Gradle property or `NUCLEUS_NODE_HOME`. To
use the `node` on `PATH` and skip the download attempt, turn provisioning off:

```kotlin title="build.gradle.kts"
nativeDistributions {
    nodejs {
        autoDownload = false
    }
}
```

See [Provision Node.js](/docs/packaging#provision-nodejs).

## Linux packaging

### AppImage takes about 60 seconds to start

**Symptom.** The app opens quickly in development but takes about a minute when packaged
as an AppImage.

**Cause.** `compressionLevel = CompressionLevel.Maximum` or `Ultra`. AppImage uses squashfs,
and maximum compression triggers FUSE decompression on every launch.

**Fix.** Use `CompressionLevel.Normal` (the default) for AppImage. Prefer a format-local
override so DEB/DMG can stay on a higher global level:

```kotlin title="build.gradle.kts"
nativeDistributions {
    compressionLevel = CompressionLevel.Ultra
    linux {
        appImage {
            compressionLevel = CompressionLevel.Normal
        }
    }
}
```

### DEB or RPM fails: "Please specify project homepage"

**Symptom.** `packageDeb` or `packageGraalvmDeb` fails immediately.

**Cause.** Unlike jpackage, electron-builder requires `homepage` for DEB.

**Fix.** Set the homepage on the distribution:

```kotlin title="build.gradle.kts"
nativeDistributions {
    homepage = "https://myapp.example.com"
}
```

### Flatpak task skips silently

**Symptom.** `packageFlatpak` reports "skipped" with no error.

**Cause.** `flatpak-builder` or the `org.freedesktop.Platform//23.08` runtime is missing
on the build host.

**Fix.** Install the tooling and runtime:

```shell
sudo apt-get install -y flatpak flatpak-builder
flatpak remote-add --if-not-exists flathub https://flathub.org/repo/flathub.flatpakrepo
flatpak install -y flathub org.freedesktop.Platform//23.08
flatpak install -y flathub org.freedesktop.Sdk//23.08
```

In CI, use `setup-nucleus` with `flatpak: 'true'`.

### Snap fails: "snapcraft: command not found"

**Symptom.** `packageSnap` fails before producing anything.

**Cause.** `snapd` or `snapcraft` is missing on the build host.

**Fix.** Install both:

```shell
sudo apt-get install -y snapd
sudo snap install snapcraft --classic
```

In CI, use `setup-nucleus` with `snap: 'true'`.

## Native libraries

### Module reports `isAvailable == false` or silent no-ops

**Symptom.** System tray, system color, notifications, or another OS-integration module
does nothing on a platform where you expect it to work. Public APIs return `null` /
`false`, or `isAvailable` is `false`.

**Cause.** The JNI shared library for that module did not load. Common reasons: no binary
for this OS/arch in the dependency JAR, the module is missing from the runtime classpath,
or extraction into the content-addressed cache failed.

**Fix.** Confirm the module dependency is on the runtime classpath and that the JAR
contains `/nucleus/native/<os>-<arch>/…` for your platform. Clear the loader cache and
relaunch if an upgrade left a partial extract:

| Platform | Cache path |
|----------|------------|
| macOS | `~/Library/Caches/nucleus/native/` |
| Linux | `~/.cache/nucleus/native/` (or `$XDG_CACHE_HOME/nucleus/native/`) |
| Windows | `%LOCALAPPDATA%\nucleus\native\` |

See [Native library loader](/docs/performance/native-library-loader) for the full load
order, JAR layout, and sidecar rules.

### Native library fails to load on an older Linux distribution

**Symptom.** On Ubuntu 22.04, Debian 12, Devuan 5, or another distribution older than
Ubuntu 24.04, the app crashes at launch or a module reports `isAvailable == false`. stderr
shows `version 'GLIBC_2.3x' not found` for a `libnucleus_*.so` library.

**Cause.** Up to 2.5.17 the Linux natives were built on `ubuntu-latest` (Ubuntu 24.04), so
they required glibc 2.39.

**Fix.** Upgrade to 2.5.18 or later. The natives are built on Ubuntu 22.04 and need
glibc 2.35 or newer. Check your system's version with `ldd --version`.

## Rendering

### Crash on launch with an older Linux GPU

**Symptom.** A window aborts at open on Linux. stderr mentions a failed GL 3.3 context, or the
process exits from `TaoComposeSceneHostLinux` with a `require()` failure.

**Cause.** Before 2.5.16, the Linux EGL attach requested only a GL 3.3 **compatibility**
profile. Some drivers (Mesa r600 on AMD RV610, for example) cap the compat profile at 3.0 while
the **core** profile reaches 3.3. The request could never succeed, and the window aborted.

**Fix.** Upgrade to 2.5.16 or later. Attach tries 3.3 compat, then 3.3 core, then Mesa llvmpipe
(`LIBGL_ALWAYS_SOFTWARE=1`, once, skipped if you already set that variable). Each fallback logs
one line on stderr. Hardware that accepts the compat request behaves as before. Set
`LIBGL_ALWAYS_SOFTWARE=1` yourself to force llvmpipe from the start.

## Event loop

### Window hangs and the log shows a thread dump

**Symptom.** On Windows, a window turns to "Not responding", and the log holds a `SEVERE` entry:
`Tao event loop has not pumped messages for at least <n> ms — the UI is frozen. Thread dump
follows.`

**Cause.** The UI thread is blocked. A deadlock or long synchronous work keeps the event loop
from pumping messages. The event-loop watchdog detects it and dumps every thread, event-loop
thread first.

**Fix.** Read the event-loop thread's stack at the top of the dump and move the blocking call
off the UI thread. For work that has to stay there, wrap it in `expectUnresponsive { }` so the
watchdog ignores it. Register `onUnresponsive` to report hangs from the field. See
[Detect a stalled event loop](/docs/concepts/threading#detect-a-stalled-event-loop).

## Input

### Custom scroll handler ignores the macOS trackpad

**Symptom.** On macOS, a `pointerInput` handler that reacts to `PointerEventType.Scroll` works
with a mouse wheel but not with a two-finger trackpad swipe. `LazyColumn` and
`Modifier.scrollable` still scroll.

<Callout type="warn" title="Changed in 3.0">
A trackpad swipe on macOS now arrives as `PanStart`, `PanMove`, and `PanEnd`. In 2.x it arrived
as `Scroll`. See [Migrate from 2.x](/docs/migrate/from-2.x).
</Callout>

**Cause.** Your handler listens only for `Scroll`, so it never sees the pan events.

**Fix.** Handle `PointerEventType.PanMove` and read `change.panOffset` next to your `Scroll`
branch. To get every trackpad step back as `Scroll`, start the JVM with
`-Dnucleus.tao.trackpadPanEvents=false`. See
[Scroll with a trackpad on macOS](/docs/input/trackpad-gestures#scroll).

### Pinch no longer reaches detectTransformGestures

**Symptom.** A trackpad pinch no longer zooms content that uses `detectTransformGestures`.

<Callout type="warn" title="Changed in 3.0">
A pinch now reaches Compose as `ScaleStart`, `ScaleChange`, and `ScaleEnd`. In 2.x it was two
synthetic touch pointers. See [Migrate from 2.x](/docs/migrate/from-2.x).
</Callout>

**Cause.** `detectTransformGestures` tracks touch pointers and does not see Scale events.

**Fix.** Move pinch handling to `Modifier.transformable` or to a listener for the `Scale*`
events. See [Zoom with a pinch](/docs/input/trackpad-gestures#zoom-with-a-pinch).

## Application lifecycle

### Cmd+Q no longer quits the app

**Symptom.** On macOS, Cmd+Q, Dock → Quit, or a logout leaves the app running.

<Callout type="warn" title="Changed in 3.0">
A system quit on macOS now calls `onCloseRequest` on every open window. In 2.x it terminated the
app without asking. See [Migrate from 2.x](/docs/migrate/from-2.x).
</Callout>

**Cause.** One of your windows has an `onCloseRequest` that neither calls `exitApplication()`
nor closes the window, for example one that hides the window to the tray. A window that stays
open vetoes the quit.

**Fix.** Let a real quit through. Check `isQuitting` on the application scope:

```kotlin
DecoratedWindow(
    onCloseRequest = {
        if (isQuitting) exitApplication() else visible = false
    },
    visible = visible,
) { /* ... */ }
```

See [Handle a system quit](/docs/lifecycle/application#handle-a-system-quit).

### Second instance is not forwarded in dev runs

**Symptom.** Under `./gradlew run` or an IDE launch, a second copy starts its own window instead
of handing its arguments to the first one.

<Callout type="warn" title="Changed in 3.0">
`enableSingleInstance` now defaults to `!ExecutableRuntime.isDev()`. In 2.x it was on in dev
runs too. See [Migrate from 2.x](/docs/migrate/from-2.x).
</Callout>

**Cause.** The single-instance lock is off in dev runs, so a debug copy can start next to a
packaged one.

**Fix.** Pass `enableSingleInstance = true` to `nucleusApplication` while you test the hand-off.
See [Enable it in dev runs](/docs/lifecycle/single-instance#enable-it-in-dev-runs).

## Development

### Hot Reload window does not open on macOS

**Symptom.** A Compose Hot Reload run on macOS starts the process, but no window appears.
`./gradlew run` works.

**Cause.** The window event loop must run on macOS thread 0, and Hot Reload's `JavaExec` task
does not pass `-XstartOnFirstThread`. The Nucleus plugin adds the flag, but only when the
project declares `nucleus.decorated-window-tao` itself. An app that gets it through
`nucleus-application` has it only as a transitive dependency, so the plugin skips the flag.

**Fix.** Declare the dependency explicitly:

```kotlin title="build.gradle.kts"
implementation("dev.nucleusframework:nucleus.decorated-window-tao:<version>")
```

## Migration

### Unresolved reference: NucleusBackend

**Symptom.** After an upgrade to 3.0, compilation fails on `NucleusBackend`,
`LocalNucleusBackend`, or the `backend =` argument of `nucleusApplication`.

**Cause.** 3.0 has a single window backend. The AWT, JBR, and JNI window modules are deleted,
and the backend selection API went with them.

**Fix.** Drop the `NucleusBackend` import, the `backend` argument, and the
`decorated-window-awt`, `-jbr`, or `-jni` dependency. See
[Remove the backend selection](/docs/migrate/from-2.x#remove-the-backend-selection).

### Unresolved reference 'JewelDecoratedWindow'

**Symptom.** The import is correct and the IDE resolves the function, but compilation fails.

**Cause.** `JewelDecoratedWindow` is an extension on `NucleusApplicationScope`. A wrapper
composable without that receiver cannot call it.

**Fix.** Make your wrapper an extension as well:

```kotlin
@Composable
fun NucleusApplicationScope.MyOnboardingWindow() {
    JewelDecoratedWindow(/* ... */) { /* content */ }
}
```

See [Toolkits](/docs/toolkits#open-a-toolkit-window).

### Jewel dependency fails to resolve on an older JDK

**Symptom.** Gradle refuses the `nucleus.decorated-window-jewel` artifact with a message about
an incompatible Java version.

**Cause.** The Jewel toolkit is compiled for JDK 25, and your build targets an older one.

**Fix.** Set the Kotlin JVM toolchain to 25:

```kotlin title="build.gradle.kts"
kotlin { jvmToolchain(25) }
```

See [Install](/docs/start/install).
