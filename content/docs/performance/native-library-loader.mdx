`NativeLibraryLoader` loads the JNI libraries of Nucleus modules, and of your own JNI bridge, in a
packaged app, a fat JAR or an IDE run. It lives in `core-runtime`, which comes with
`nucleus-application`.

## Load a library

```kotlin
import dev.nucleusframework.core.runtime.NativeLibraryLoader

private val loaded: Boolean = NativeLibraryLoader.load(
    "nucleus_systemcolor",
    NativeWindowsSystemColorBridge::class.java,
)
```

`load` returns `true` once the library is in the process, and `false` when no binary exists for
this platform or loading failed. It does not throw: treat `false` as "not available". A second
call with the same name returns `true` without reloading.

| Parameter | Default | Role |
|-----------|---------|------|
| `libraryName` | required | Base name without `lib` or extension, for example `"nucleus_systemcolor"` |
| `callerClass` | required | A class from the JAR that holds the library |
| `resourcePrefix` | `"/nucleus/native"` | Root folder inside the JAR |
| `sidecarFiles` | `emptyList()` | Helper files extracted next to the library before it loads |

Put the binaries in the JAR under `{resourcePrefix}/{os}-{arch}/`, with `os` one of `darwin`,
`linux`, `win32` and `arch` one of `x64`, `aarch64`:

```text
/nucleus/native/darwin-aarch64/libnucleus_systemcolor.dylib
/nucleus/native/linux-x64/libnucleus_systemcolor.so
/nucleus/native/win32-x64/nucleus_systemcolor.dll
```

<Callout type="warn" title="Changed in 3.0">
Packaged apps no longer carry Nucleus JNI libraries inside their JARs: the plugin ships them next
to the app. Code that read them as classpath resources in a packaged app must load them through
`NativeLibraryLoader`. See [Migrate from 2.x](/docs/migrate/from-2.x).
</Callout>

## Sidecar files

Pass helper DLLs that the library needs next to it, as named in the JAR resource folder:

```kotlin
NativeLibraryLoader.load(
    "sample_tao_webview",
    SampleWebViewWindowsBridge::class.java,
    sidecarFiles = listOf("WebView2Loader.dll"),
)
```

## Relocate the cache

Fat JARs, IDE runs and distributions built without the plugin extract libraries to a per-user
cache: `~/Library/Caches/nucleus/native/` on macOS, `$XDG_CACHE_HOME/nucleus/native/` (or
`~/.cache/…`) on Linux, `%LOCALAPPDATA%\nucleus\native\` on Windows. Apps packaged by the plugin
extract nothing.

To move the root, set `nucleus.native.cacheDir` in `jvmArgs`. It covers libraries that load before
your code runs:

```kotlin title="build.gradle.kts"
nucleus.application {
    jvmArgs("-Dnucleus.native.cacheDir=/var/lib/myapp/native")
}
```

The JVM does not expand `${user.home}` there. For a path computed at run time, set it from code
before the first native load:

```kotlin
fun main(args: Array<String>) {
    NativeLibraryLoader.cacheDirectory = Path(System.getProperty("user.home"), ".myapp", "native")
    nucleusApplication(args) { /* ... */ }
}
```

The system property wins over `cacheDirectory`. A later assignment is ignored with a warning. Do
not point the cache at the install directory or inside a macOS `.app`: a standard user cannot
write there, and writing inside the bundle breaks its signature.

## JNI exceptions in the logs

When a Kotlin listener throws inside a native callback, Nucleus logs it as a `WARNING` from the
`dev.nucleusframework.core.runtime.JniExceptionReporter` logger, even when
`allowNucleusRuntimeLogging` is off. Before 3.0 these exceptions disappeared.

## Debugging

| Situation | What to check |
|-----------|---------------|
| A module reports `isAvailable == false` | Does the dependency JAR contain `/nucleus/native/<os>-<arch>/` for your platform, or does the packaged app folder contain the library? |
| Load fails after an upgrade in an IDE or fat-JAR run | Delete the cache root and relaunch. |
| A warning says the cache directory is unusable | The configured directory cannot be written. The loader moved on to the next candidate. |
| `Failed to load … native library` | Enable `FINE` logging for `dev.nucleusframework.core.runtime.NativeLibraryLoader`. |

In app code, check a module's `isAvailable` flag instead of calling `NativeLibraryLoader`.

<Accordion title="Under the hood">

- Load order: the `nucleus.native.libraryPath` directory (set by the plugin's launcher), then
  `System.loadLibrary` on `java.library.path` (sandboxed store builds, GraalVM native images), then
  extraction from the JAR.
- jpackage builds keep the libraries in `$APPDIR` next to Skiko; native images keep them next to
  the executable (`Contents/MacOS/` on macOS). Only libraries listed in a Nucleus module's
  `META-INF/nucleus/native-libraries/` manifest move; yours stay in their JARs.
- A missing resource logs at `FINE` and returns `false`, so a macOS-only module stays silent on Linux.
- Cache layout: `<root>/<os>-<arch>/<fingerprint>/<file>`. The fingerprint comes from the JAR
  entry's CRC-32 and size (size and mtime for `file:` URLs); sidecars share it. Extraction writes
  a temp file and renames it.
- Cache root order: `nucleus.native.cacheDir`, then `cacheDirectory`, then the platform default.
  The loader checks each with a real write probe and falls through on failure. An empty or
  relative `XDG_CACHE_HOME` or `LOCALAPPDATA` is ignored.
- The JNI exception message is `Native JNI callback cleared a pending Kotlin exception`, logged
  through `java.util.logging` with the throwable attached.
- [Native code in Kotlin](/docs/performance/native-code) has its own, independent loader
  (`~/.cache/kne/`, `kne/native/`).

</Accordion>
