`native-ssl` lit les certificats racines auxquels le système d'exploitation fait confiance sous
macOS, Windows et Linux, les fusionne avec ceux de la JVM et expose le résultat sous la forme d'un
unique `X509TrustManager`. Les handshakes HTTPS vers des hôtes signés par une racine d'entreprise,
un profil MDM ou un proxy d'inspection TLS aboutissent alors.

## Ajouter la dépendance

```kotlin title="build.gradle.kts"
dependencies {
    implementation("dev.nucleusframework:nucleus.native-ssl:<version>")
}
```

<Callout type="tip">
Pour `java.net.http`, OkHttp ou Ktor, ajoutez plutôt un adaptateur [HTTP natif](/docs/performance/native-http).
Il branche `native-ssl` sur le client.
</Callout>

## Obtenir un trust manager

Lisez la propriété attendue par votre pile TLS :

```kotlin
import dev.nucleusframework.nativessl.NativeTrustManager

val trustManager: X509TrustManager = NativeTrustManager.trustManager
val sslContext: SSLContext = NativeTrustManager.sslContext
val sslSocketFactory: SSLSocketFactory = NativeTrustManager.sslSocketFactory
```

La première lecture construit le trust manager et le garde en cache pour toute la vie du
processus. Les certificats ajoutés au magasin de l'OS ensuite restent invisibles jusqu'au
redémarrage de l'application. Vous ne pouvez pas brancher de source de certificats personnalisée.

## ProGuard

Les règles ProGuard par défaut du plugin Nucleus couvrent ce module. Si vous les remplacez par les
vôtres, conservez les deux bridges :

```proguard
-keep class dev.nucleusframework.nativessl.mac.NativeSslBridge {
    native <methods>;
}
-keep class dev.nucleusframework.nativessl.windows.WindowsSslBridge {
    native <methods>;
}
```

## Logs

Le module journalise le nombre et la source des certificats en `FINE` sur le logger
`dev.nucleusframework.nativessl`. Passez ce logger en `FINE`, ou définissez
`allowNucleusRuntimeLogging = true` (`dev.nucleusframework.core.runtime.tools`) depuis `main()`.

<Accordions>
<Accordion title="En coulisses">

- Le trust manager charge les émetteurs par défaut de la JVM et les certificats de l'OS dans un
  `KeyStore` en mémoire. Quand l'OS n'en signale aucun, `trustManager` est celui de la JVM.
- macOS et Windows lisent le magasin via la bibliothèque JNI `nucleus_ssl`. Si elle ne se charge
  pas, macOS n'apporte rien, et Windows se rabat sur les keystores `SunMSCAPI`
  (`Windows-ROOT`, `Windows-CA`, `Windows-MY`).
- **macOS :** les ancres système plus les domaines de réglages de confiance utilisateur et admin,
  filtrés selon les règles de [JetBrains jvm-native-trusted-roots](https://github.com/JetBrains/jvm-native-trusted-roots)
  (entrées `TrustRoot` auto-signées, politique SSL seule, contraintes inconnues rejetées).
- **Windows :** les magasins `ROOT` et `CA` de `CURRENT_USER`, `LOCAL_MACHINE`, des deux
  emplacements Group Policy et de `LOCAL_MACHINE_ENTERPRISE`, qui couvrent les déploiements Active
  Directory que `SunMSCAPI` ignore. Les entrées `ROOT` sont gardées telles quelles ; les entrées
  `CA` doivent passer la validation de chaîne. Les doublons sont retirés par empreinte SHA-1.
- **Linux :** chaque bundle ou dossier PEM lisible de la liste utilisée par `crypto/x509` de Go,
  comme `/etc/ssl/certs/ca-certificates.crt` (Debian, Ubuntu), `/etc/pki/tls/certs/ca-bundle.crt`
  (Fedora) et `/etc/ssl/cert.pem` (Alpine), dédoublonnés par contenu DER. Aucune bibliothèque native.

</Accordion>
</Accordions>

## Référence de l'API

| Propriété | Valeur |
|-----------|--------|
| `trustManager: X509TrustManager` | Racines par défaut de la JVM plus celles de l'OS |
| `sslContext: SSLContext` | Un contexte `TLS` initialisé avec `trustManager` |
| `sslSocketFactory: SSLSocketFactory` | `sslContext.socketFactory` |
