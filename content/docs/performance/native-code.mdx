NucleusNativeAccess lets you write code in Kotlin/Native and call it from the JVM as a regular
Kotlin class, with no JNI and no C. Use it for a platform API that no Nucleus module covers.

<Callout type="info" title="Separate repository">
NucleusNativeAccess ships from [`NucleusFramework/NucleusNativeAccess`](https://github.com/NucleusFramework/NucleusNativeAccess)
as the Gradle plugin `dev.nucleusframework.nna`, with its own version. It needs JDK 22 or later at
run time (25 recommended), Kotlin 2.3.20 and Gradle 9.1.
<Version module="nna" />
</Callout>

## Create the native module

Put the native code in its own Gradle module, without the Compose compiler plugin: Compose does
not support the extra Kotlin/Native compilations the bridge needs.

```kotlin title="native/build.gradle.kts"
plugins {
    kotlin("multiplatform") version "2.3.20"
    id("dev.nucleusframework.nna") version "<version>"
}

kotlin {
    jvmToolchain(25)
    jvm()
    linuxX64() // or macosArm64(), mingwX64()
}

kotlinNativeExport {
    nativeLibName = "mylib" // libmylib.so, libmylib.dylib or mylib.dll
    buildType = "release"   // "release" (default) or "debug"
}
```

Then add `implementation(project(":native"))` to the app's `jvmMain` dependencies. Nucleus
already passes `--enable-native-access=ALL-UNNAMED` to `run`, the packaged app and native images.

## Write the native class

Only the public API crosses the boundary:

```kotlin title="native/src/nativeMain/kotlin/com/example/Calculator.kt"
package com.example

class Calculator(initial: Int = 0) {
    private var acc = initial

    fun add(value: Int): Int { acc += value; return acc }
    val current: Int get() = acc
}
```

## Call it from the JVM

The generated proxy has the same shape and implements `AutoCloseable`. Closing it releases the
native object:

```kotlin title="app/src/jvmMain/kotlin/com/example/Main.kt"
Calculator(0).use { calc ->
    calc.add(5)
    println(calc.current) // 5
}
```

## Supported types

Primitives, `String`, `ByteArray`, collections, data classes, enums, nullable types, objects,
`suspend fun`, `Flow<T>`, lambdas and exceptions (rethrown as `KotlinNativeException`) all cross
the bridge. Classes, inheritance, interfaces, sealed classes, companion objects, default parameters
and extensions on your own classes carry over.

The bridge does not support:

- Generics. Use concrete types.
- An interface or sealed class as a return type. Return the concrete class.
- Operator overloading and infix functions.
- Extension functions on standard library types.
- `ByteArray` inside collections, data class fields or callback parameters.
- Subclassing a native class from the JVM.
- Kotlin/Native-only types such as `CPointer` in the public API.

## Wrap a C library

Declare `cinterop` bindings in the native module, wrap them in a Kotlin class in `nativeMain`, and
keep C types such as `CPointer` inside that class:

```kotlin title="native/build.gradle.kts"
kotlin {
    linuxX64().compilations["main"].cinterops {
        val libnotify by creating { defFile(project.file("src/nativeInterop/cinterop/libnotify.def")) }
    }
}
```

```kotlin title="native/src/nativeMain/kotlin/com/example/LinuxDesktop.kt"
class LinuxDesktop {
    fun sendNotification(title: String, body: String, icon: String): Boolean {
        notify_init("MyApp")
        val n = notify_notification_new(title, body, icon) ?: return false
        return notify_notification_show(n, null) != 0
    }
}
```

## Build a native image

The plugin writes the GraalVM metadata for you. A native image cannot extract the library from the
JAR, so ship `libmylib` next to the executable.

<Accordions>
<Accordion title="Under the hood">

- The plugin reads the public API of `nativeMain`, generates `@CName` bridge functions that track
  each object with a `StableRef`, and JVM proxies that call them through FFM downcalls.
- The library ships in the JAR under `kne/native/{os}-{arch}/`. At run time the proxy tries
  `java.library.path`, then extracts to `~/.cache/kne/`, then the loader lookup native images need.
- A `Cleaner` releases native objects whose proxies you never closed.
- GraalVM metadata lives under `META-INF/native-image/kne/{libName}/` (`reflect-config.json`,
  `resource-config.json`, `reachability-metadata.json`). See [Automatic metadata](/docs/performance/graalvm/automatic-metadata).
- This loader is separate from the [Nucleus native library loader](/docs/performance/native-library-loader).

</Accordion>
