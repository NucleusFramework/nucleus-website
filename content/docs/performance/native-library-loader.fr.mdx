`NativeLibraryLoader` charge les bibliothèques JNI des modules Nucleus, et celles de votre propre
pont JNI, dans une application empaquetée, un fat JAR ou une exécution depuis l'IDE. Il se trouve
dans `core-runtime`, fourni avec `nucleus-application`.

## Charger une bibliothèque

```kotlin
import dev.nucleusframework.core.runtime.NativeLibraryLoader

private val loaded: Boolean = NativeLibraryLoader.load(
    "nucleus_systemcolor",
    NativeWindowsSystemColorBridge::class.java,
)
```

`load` renvoie `true` une fois la bibliothèque chargée dans le processus, et `false` quand aucun
binaire n'existe pour cette plateforme ou que le chargement a échoué. Il ne lève pas d'exception :
traitez `false` comme « indisponible ». Un second appel avec le même nom renvoie `true` sans
recharger.

| Paramètre | Défaut | Rôle |
|-----------|--------|------|
| `libraryName` | requis | Nom de base sans `lib` ni extension, par exemple `"nucleus_systemcolor"` |
| `callerClass` | requis | Une classe du JAR qui contient la bibliothèque |
| `resourcePrefix` | `"/nucleus/native"` | Dossier racine dans le JAR |
| `sidecarFiles` | `emptyList()` | Fichiers annexes extraits à côté de la bibliothèque avant son chargement |

Placez les binaires dans le JAR sous `{resourcePrefix}/{os}-{arch}/`, avec `os` parmi `darwin`,
`linux`, `win32` et `arch` parmi `x64`, `aarch64` :

```text
/nucleus/native/darwin-aarch64/libnucleus_systemcolor.dylib
/nucleus/native/linux-x64/libnucleus_systemcolor.so
/nucleus/native/win32-x64/nucleus_systemcolor.dll
```

<Callout type="warn" title="Modifié en 3.0">
Les applications empaquetées ne portent plus les bibliothèques JNI de Nucleus dans leurs JAR : le
plugin les livre à côté de l'application. Le code qui les lisait comme ressources du classpath dans
une application empaquetée doit passer par `NativeLibraryLoader`. Voir
[Migrer depuis la 2.x](/docs/migrate/from-2.x).
</Callout>

## Fichiers annexes

Passez les DLL annexes dont la bibliothèque a besoin à côté d'elle, nommées comme dans le dossier
de ressources du JAR :

```kotlin
NativeLibraryLoader.load(
    "sample_tao_webview",
    SampleWebViewWindowsBridge::class.java,
    sidecarFiles = listOf("WebView2Loader.dll"),
)
```

## Déplacer le cache

Les fat JAR, les exécutions depuis l'IDE et les distributions construites sans le plugin extraient
les bibliothèques dans un cache par utilisateur : `~/Library/Caches/nucleus/native/` sur macOS,
`$XDG_CACHE_HOME/nucleus/native/` (ou `~/.cache/…`) sur Linux, `%LOCALAPPDATA%\nucleus\native\`
sur Windows. Les applications empaquetées par le plugin n'extraient rien.

Pour déplacer la racine, définissez `nucleus.native.cacheDir` dans `jvmArgs`. La propriété couvre
les bibliothèques chargées avant votre code :

```kotlin title="build.gradle.kts"
nucleus.application {
    jvmArgs("-Dnucleus.native.cacheDir=/var/lib/myapp/native")
}
```

La JVM n'y développe pas `${user.home}`. Pour un chemin calculé à l'exécution, définissez-le depuis
le code avant le premier chargement natif :

```kotlin
fun main(args: Array<String>) {
    NativeLibraryLoader.cacheDirectory = Path(System.getProperty("user.home"), ".myapp", "native")
    nucleusApplication(args) { /* ... */ }
}
```

La propriété système l'emporte sur `cacheDirectory`. Une affectation tardive est ignorée avec un
avertissement. Ne pointez pas le cache vers le dossier d'installation ni dans un `.app` macOS : un
utilisateur standard ne peut pas y écrire, et une écriture dans le bundle casse sa signature.

## Exceptions JNI dans les logs

Quand un listener Kotlin lève une exception dans un callback natif, Nucleus la journalise en
`WARNING` sur le logger `dev.nucleusframework.core.runtime.JniExceptionReporter`, même quand
`allowNucleusRuntimeLogging` est désactivé. Avant la 3.0, ces exceptions disparaissaient.

## Débogage

| Situation | À vérifier |
|-----------|------------|
| Un module indique `isAvailable == false` | Le JAR de la dépendance contient-il `/nucleus/native/<os>-<arch>/` pour votre plateforme, ou le dossier de l'application empaquetée contient-il la bibliothèque ? |
| Le chargement échoue après une mise à jour, en IDE ou en fat JAR | Supprimez la racine du cache et relancez. |
| Un avertissement signale un dossier de cache inutilisable | Le dossier configuré n'accepte pas l'écriture. Le chargeur est passé au candidat suivant. |
| `Failed to load … native library` | Activez les logs `FINE` pour `dev.nucleusframework.core.runtime.NativeLibraryLoader`. |

Dans le code de l'application, testez l'indicateur `isAvailable` d'un module plutôt que d'appeler
`NativeLibraryLoader`.

<Accordion title="En coulisses">

- Ordre de chargement : le dossier `nucleus.native.libraryPath` (défini par le lanceur du plugin),
  puis `System.loadLibrary` sur `java.library.path` (builds sandboxés pour les stores, images
  natives GraalVM), puis l'extraction depuis le JAR.
- Les builds jpackage placent les bibliothèques dans `$APPDIR` à côté de Skiko ; les images natives
  à côté de l'exécutable (`Contents/MacOS/` sur macOS). Seules les bibliothèques listées dans le
  manifeste `META-INF/nucleus/native-libraries/` d'un module Nucleus sont déplacées ; les vôtres
  restent dans leurs JAR.
- Une ressource absente est journalisée en `FINE` et renvoie `false` : un module réservé à macOS
  reste silencieux sous Linux.
- Organisation du cache : `<root>/<os>-<arch>/<fingerprint>/<file>`. L'empreinte vient du CRC-32
  et de la taille de l'entrée du JAR (taille et date de modification pour les URL `file:`) ; les
  fichiers annexes la partagent. L'extraction écrit un fichier temporaire puis le renomme.
- Ordre de la racine du cache : `nucleus.native.cacheDir`, puis `cacheDirectory`, puis la valeur par
  défaut de la plateforme. Le chargeur teste chacune par une vraie écriture et passe à la suivante
  en cas d'échec. Un `XDG_CACHE_HOME` ou `LOCALAPPDATA` vide ou relatif est ignoré.
- Le message d'exception JNI est `Native JNI callback cleared a pending Kotlin exception`, émis via
  `java.util.logging` avec le throwable joint.
- [Du code natif en Kotlin](/docs/performance/native-code) a son propre chargeur, indépendant
  (`~/.cache/kne/`, `kne/native/`).
