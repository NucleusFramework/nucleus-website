NucleusNativeAccess vous permet d'écrire du code en Kotlin/Native et de l'appeler depuis la JVM
comme une classe Kotlin ordinaire, sans JNI ni C. Servez-vous-en pour une API de plateforme
qu'aucun module Nucleus ne couvre.

<Callout type="info" title="Dépôt séparé">
NucleusNativeAccess est livré depuis [`NucleusFramework/NucleusNativeAccess`](https://github.com/NucleusFramework/NucleusNativeAccess)
sous la forme du plugin Gradle `dev.nucleusframework.nna`, avec sa propre version. Il demande le
JDK 22 ou plus récent à l'exécution (25 recommandé), Kotlin 2.3.20 et Gradle 9.1.
<Version module="nna" lang="fr" />
</Callout>

## Créer le module natif

Placez le code natif dans un module Gradle à part, sans le plugin du compilateur Compose : Compose
ne gère pas les compilations Kotlin/Native supplémentaires dont le pont a besoin.

```kotlin title="native/build.gradle.kts"
plugins {
    kotlin("multiplatform") version "2.3.20"
    id("dev.nucleusframework.nna") version "<version>"
}

kotlin {
    jvmToolchain(25)
    jvm()
    linuxX64() // or macosArm64(), mingwX64()
}

kotlinNativeExport {
    nativeLibName = "mylib" // libmylib.so, libmylib.dylib or mylib.dll
    buildType = "release"   // "release" (default) or "debug"
}
```

Ajoutez ensuite `implementation(project(":native"))` aux dépendances `jvmMain` de l'application.
Nucleus passe déjà `--enable-native-access=ALL-UNNAMED` à `run`, à l'application empaquetée et aux
images natives.

## Écrire la classe native

Seule l'API publique traverse la frontière :

```kotlin title="native/src/nativeMain/kotlin/com/example/Calculator.kt"
package com.example

class Calculator(initial: Int = 0) {
    private var acc = initial

    fun add(value: Int): Int { acc += value; return acc }
    val current: Int get() = acc
}
```

## L'appeler depuis la JVM

Le proxy généré a la même forme et implémente `AutoCloseable`. Sa fermeture libère l'objet
natif :

```kotlin title="app/src/jvmMain/kotlin/com/example/Main.kt"
Calculator(0).use { calc ->
    calc.add(5)
    println(calc.current) // 5
}
```

## Types pris en charge

Primitifs, `String`, `ByteArray`, collections, data classes, enums, types nullables, objets,
`suspend fun`, `Flow<T>`, lambdas et exceptions (relancées en `KotlinNativeException`) traversent
le pont. Les classes, l'héritage, les interfaces, les sealed classes, les companion objects, les
paramètres par défaut et les extensions sur vos propres classes sont exportés.

Le pont ne gère pas :

- Les génériques. Utilisez des types concrets.
- Une interface ou une sealed class en type de retour. Renvoyez la classe concrète.
- La surcharge d'opérateurs et les fonctions infix.
- Les fonctions d'extension sur les types de la bibliothèque standard.
- `ByteArray` dans une collection, un champ de data class ou un paramètre de callback.
- L'héritage d'une classe native depuis la JVM.
- Les types propres à Kotlin/Native, comme `CPointer`, dans l'API publique.

## Envelopper une bibliothèque C

Déclarez des bindings `cinterop` dans le module natif, enveloppez-les dans une classe Kotlin de
`nativeMain`, et gardez les types C comme `CPointer` à l'intérieur de cette classe :

```kotlin title="native/build.gradle.kts"
kotlin {
    linuxX64().compilations["main"].cinterops {
        val libnotify by creating { defFile(project.file("src/nativeInterop/cinterop/libnotify.def")) }
    }
}
```

```kotlin title="native/src/nativeMain/kotlin/com/example/LinuxDesktop.kt"
class LinuxDesktop {
    fun sendNotification(title: String, body: String, icon: String): Boolean {
        notify_init("MyApp")
        val n = notify_notification_new(title, body, icon) ?: return false
        return notify_notification_show(n, null) != 0
    }
}
```

## Compiler une image native

Le plugin écrit les métadonnées GraalVM à votre place. Une image native ne peut pas extraire la
bibliothèque du JAR : livrez `libmylib` à côté de l'exécutable.

<Accordions>
<Accordion title="En coulisses">

- Le plugin lit l'API publique de `nativeMain`, génère des fonctions de pont `@CName` qui suivent
  chaque objet avec un `StableRef`, et des proxies JVM qui les appellent par des downcalls FFM.
- La bibliothèque est embarquée dans le JAR sous `kne/native/{os}-{arch}/`. À l'exécution, le
  proxy essaie `java.library.path`, puis extrait vers `~/.cache/kne/`, puis passe par la recherche
  du loader dont les images natives ont besoin.
- Un `Cleaner` libère les objets natifs dont vous n'avez jamais fermé le proxy.
- Les métadonnées GraalVM se trouvent sous `META-INF/native-image/kne/{libName}/`
  (`reflect-config.json`, `resource-config.json`, `reachability-metadata.json`). Voir
  [Métadonnées automatiques](/docs/performance/graalvm/automatic-metadata).
- Ce chargeur est distinct du [chargeur de bibliothèques natives de Nucleus](/docs/performance/native-library-loader).

</Accordion>
