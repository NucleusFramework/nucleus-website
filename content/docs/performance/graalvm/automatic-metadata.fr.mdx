Le plugin Nucleus génère les métadonnées de réflexion, de ressources et JNI dont `native-image` a
besoin : un build natif fonctionne sans `reachability-metadata.json` écrit à la main. Il couvre
Compose, Ktor, kotlinx.serialization, SQLite, Coil et le JDK, vos autres dépendances via le
[GraalVM Reachability Metadata Repository](https://github.com/oracle/graalvm-reachability-metadata),
et les appels littéraux à `Class.forName()`, `getResource()` et aux méthodes natives de votre code.

## Détecter les classes orphelines du projet

Les `*_Impl` de Room, les `*_Factory` de Dagger et les adaptateurs Moshi sont chargés par leur nom :
aucun bytecode ne les référence. Le plugin enregistre une telle classe quand elle est publique,
possède un constructeur public sans argument, et que votre code référence l'un de ses supertypes.
Le log de build affiche `[orphan] <fqcn>` pour chacune.

`detectOrphanProjectClasses` est actif par défaut. `reflectionForProjectClasses = true` enregistre
toutes les classes du projet dotées d'un constructeur public sans argument ; ne l'utilisez que pour
débloquer un build, car il alourdit l'image.

## Combler les manques avec l'agent de traçage

L'analyse à la compilation ne voit pas la réflexion pilotée par des valeurs d'exécution. Lancez
l'agent une fois avant une release et parcourez chaque écran :

```shell
./gradlew runWithNativeAgent
```

L'agent fusionne les nouvelles entrées dans votre `reachability-metadata.json` et conserve celles
que vous avez modifiées. Committez ce fichier. Pour le placer dans un autre dossier, définissez
`graalvm { nativeImageConfigBaseDir }`. Pour repérer les manques plus tôt, voir
[Repérer les enregistrements manquants](/docs/performance/graalvm/configuration#repérer-les-enregistrements-manquants-pendant-le-développement).

## Nettoyer les entrées manuelles

```shell
./gradlew cleanupGraalvmMetadata
# Retirer aussi les entrées dont les types ne sont sur aucun classpath
./gradlew cleanupGraalvmMetadata -Pnucleus.graalvm.cleanup.removeUnresolvable=true
# Produire le rapport sans réécrire le fichier
./gradlew cleanupGraalvmMetadata -Pnucleus.graalvm.cleanup.dryRun=true
```

La tâche retire les entrées déjà couvertes par les métadonnées générées et liste celles qu'elle
conserve. Une entrée `kept` n'est couverte par rien d'autre : vérifiez-la.

Le plugin fusionne cinq sources, chacune passée par son propre `-H:ConfigurationFileDirectories=` :

1. 29 fichiers de métadonnées dans le JAR du plugin, conservés quand leurs `matchPackages` sont sur
   le classpath (`filterGraalvmLibraryMetadata`). Les builds headless retirent les packs
   graphiques.
2. Le Reachability Metadata Repository, version `1.1.4` (`resolveGraalvmReachabilityMetadata`).
3. Les métadonnées de plateforme pour `sun.awt.windows.*`, `sun.lwawt.macosx.*` ou
   `sun.awt.X11.*`, Java2D, les gestionnaires de polices, les fournisseurs de sécurité et `main`
   (`generateGraalvmPlatformMetadata`).
4. Une analyse du bytecode du classpath d'exécution (`analyzeGraalvmStaticMetadata`). Elle repère
   aussi `MethodHandles.Lookup.findClass()`, les rappels JNI et les companions `@Serializable`. Le
   détecteur d'orphelines lit les dossiers de la cible JVM de l'application, comme
   `desktopMainClasses`.
5. Les métadonnées embarquées dans `nucleus.graalvm-runtime` : globs de ressources (`**/*.svg`,
   `**/*.ttf`, `composeResources/**`, `META-INF/services/**`, …), `-H:+SharedArenaSupport`, et
   substitutions AWT pour les polices et l'écran de démarrage.

`cleanupGraalvmMetadata` compare votre fichier aux sources 1 à 4. Il retire toujours les types
Kotlin fantômes enregistrés par l'agent (`kotlin.Any`, `FunctionN`, …) et ne retire jamais les
types des packages de `exactReachabilityMetadata`.
