Une app Nucleus empaquetée tourne en un seul process. Un second lancement transmet son
[deep link](/docs/lifecycle/deep-links) au process en cours, qui affiche et met au premier plan
chaque `DecoratedWindow`, puis se termine avant le démarrage de Compose. `nucleusApplication` s'en
charge sans code, de la même façon sous macOS, Windows et Linux.

## L'activer en dev

`./gradlew run` et les lancements depuis l'IDE ignorent le verrou : une seconde copie de debug
démarre normalement. Activez-le pour tester le transfert, ou passez `false` pour le désactiver
aussi dans les builds empaquetés :

```kotlin
fun main(args: Array<String>) = nucleusApplication(args, enableSingleInstance = true) {
    // ...
}
```

<Callout type="warn" title="Modifié en 3.0">
En 2.x, `enableSingleInstance` valait aussi `true` en dev. Il vaut désormais
`!ExecutableRuntime.isDev()`. Voir [Migrer depuis 2.x](/docs/migrate/from-2.x).
</Callout>

## Réagir à un second lancement

Quand votre surface principale n'est pas un `DecoratedWindow`, par exemple une popup de tray,
restaurez-la vous-même. Le callback s'exécute sur le thread UI :

```kotlin
SingleInstanceRestoreEffect { popupVisible = true }
```

## Câbler manuellement

Sans `nucleusApplication`, appelez `SingleInstanceManager.isSingleInstance` en tête de `main`,
avant de construire l'UI :

```kotlin
fun main(args: Array<String>) {
    val isPrimary = SingleInstanceManager.isSingleInstance(
        onRestoreFileCreated = {
            // Second instance. `this` est le Path de restauration : écrivez la charge utile.
        },
        onRestoreRequest = {
            // Process principal, sur un thread de fond.
            NucleusUiThread.post { bringMainWindowToFront() }
        },
    )
    if (!isPrimary) exitProcess(0)
    startUi(args)
}
```

`onRestoreFileCreated` est optionnel. Pour transmettre un URI, utilisez
[`DeepLinkHandler.writeUriTo`](/docs/lifecycle/deep-links).

Le verrou porte le nom de l'id d'app et vit dans le dossier temporaire de l'utilisateur : deux
apps n'entrent jamais en conflit, et deux utilisateurs peuvent chacun lancer l'app.

<Accordions>
<Accordion title="En coulisses">

- Le verrou est un `java.nio.channels.FileLock` sur `<lockIdentifier>.lock`. Le noyau le libère
  quand la JVM se termine ou plante : un process principal tué ne bloque pas l'app.
- Un second lancement écrit `<lockIdentifier>.restore_request` à côté. Le process principal
  surveille le dossier avec un `WatchService` et appelle `onRestoreRequest`.
- Un fichier de verrou périmé ou illisible est supprimé et le verrou retenté une fois. Seule une
  erreur irrécupérable fait continuer le process en tant que principal.

</Accordion>
</Accordions>

## Référence de l'API

| Symbole | Notes |
|---|---|
| `SingleInstanceManager.isSingleInstance(onRestoreFileCreated, onRestoreRequest): Boolean` | `true` dans le process principal. `onRestoreRequest` s'exécute sur un thread daemon. |
| `SingleInstanceManager.configuration` | À assigner avant le premier appel à `isSingleInstance`, sinon `IllegalStateException`. |
| `Configuration.lockFilesDir` | Dossier du verrou. Défaut : `java.io.tmpdir`. |
| `Configuration.lockIdentifier` | Nom de base des fichiers de verrou. Défaut : l'id d'app. |
| `SingleInstanceRestoreEffect(onRestore)` | Composable de `dev.nucleusframework.application`. S'exécute à chaque second lancement. |
