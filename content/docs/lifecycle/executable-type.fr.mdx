`ExecutableRuntime` indique comment le process courant a été empaqueté (DMG, APPX, Flatpak, Snap,
`./gradlew run`, etc.) et s'il tourne dans un sandbox de l'OS. Utilisez-le pour choisir un canal
de mise à jour ou désactiver une fonction que le sandbox interdit. Il est fourni par
`core-runtime`, qu'apporte `nucleus-application`.

## Détecter le format de packaging

```kotlin
when (ExecutableRuntime.type()) {
    ExecutableType.APPX    -> showMicrosoftStoreUpdate()
    ExecutableType.SNAP    -> showSnapStoreUpdate()
    ExecutableType.FLATPAK -> showFlathubUpdate()
    ExecutableType.DEV     -> Unit // pas de mise à jour en développement
    else                   -> checkForUpdatesDirectly()
}
```

Pour un seul format, utilisez le test correspondant, comme `ExecutableRuntime.isDev()`. Tout
lancement non empaqueté renvoie `DEV`, tout comme un type inconnu ou absent : `DEV` ne distingue
donc pas un lancement depuis l'IDE d'un package mal configuré. En dev, `nucleusApplication` ignore
le [verrou d'instance unique](/docs/lifecycle/single-instance) et
[`AutoLaunch.wasStartedAtLogin`](/docs/lifecycle/background/launch-at-login) renvoie `false`.

## Détecter un sandbox

`isSandboxed()` renvoie `true` dans l'App Sandbox de macOS, un conteneur AppX ou un Flatpak.
Conditionnez le code sensible au sandbox sur ce test, pas sur le format : sur macOS, un PKG
construit avec `macOS { pkg { appStore = false } }` n'est pas sandboxé, alors que le PKG App
Store l'est.

```kotlin
if (!ExecutableRuntime.isSandboxed()) {
    registerLaunchdTask()
}
```

<Callout type="warn" title="Modifié en 3.0">
Le code qui testait `isPkg()` pour détecter le sandbox du Mac App Store se trompe désormais sur
les PKG Developer ID. Testez `isSandboxed()` à la place. Voir
[Migrer depuis 2.x](/docs/migrate/from-2.x).
</Callout>

Les formats qui produisent une app sandboxée sont décrits dans
[Sandboxing](/docs/packaging/sandboxing).

<Accordions>
<Accordion title="En coulisses">

- Le plugin enregistre le format au build : `-Dnucleus.executable.type=<kind>` dans le `.cfg` du
  lanceur pour les apps JVM, ou un marqueur `.nucleus-executable-type` à côté de l'exécutable
  d'une image native (`Contents/Resources/` sur macOS). `type()` lit la propriété, puis le
  marqueur.
- Sur macOS, `isSandboxed()` lit `APP_SANDBOX_CONTAINER_ID`, que macOS définit dans chaque
  process sandboxé.
- `aot-runtime` réexporte les deux types en alias de type pour le code purement AOT.

</Accordion>

## Référence de l'API

| Membre | Renvoie | Notes |
|---|---|---|
| `type()` | `ExecutableType` | Le format de packaging. |
| `type(propertyName)` | `ExecutableType` | Lit le format depuis une autre propriété système. |
| `parseType(rawValue)` | `ExecutableType` | Analyse une chaîne brute. Une entrée inconnue donne `DEV`. |
| `isSandboxed()` | `Boolean` | `true` dans l'App Sandbox de macOS, un conteneur AppX ou un Flatpak. |
| `markerVersion()` | `String?` | Version de l'app lue dans le marqueur (images natives). Pour la version en général, lisez [`NucleusApp.version`](/docs/lifecycle/app-metadata). |
| `isGraalVmNativeImage` | `Boolean` | `true` dans une image native GraalVM. |
| `isExe()` … `isDev()` | `Boolean` | Un test par valeur d'`ExecutableType`. |

Valeurs d'`ExecutableType` :

- Windows : `EXE`, `MSI`, `NSIS`, `NSIS_WEB`, `PORTABLE`, `APPX`
- macOS : `DMG`, `PKG`
- Linux : `DEB`, `RPM`, `SNAP`, `FLATPAK`, `APPIMAGE`, `PACMAN`
- Archives : `ZIP`, `TAR`, `SEVEN_Z`
- Développement : `DEV`
